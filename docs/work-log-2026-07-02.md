因此今天没有从零手写 Gazebo camera 插件，而是复用 Husky 自带的 RealSense 仿真结构。这样做的好处是改动小，和上游 Husky 的模型组织方式一致，也能同时得到 RGB 图像、深度图和深度点云。

在本地集成 launch 中新增了 RealSense 参数，并默认启用 D435：

```text
realsense_xyz:=0.35 0 0.12
realsense_rpy:=0 0 0
```

相机安装在 `top_plate_link` 前方，topic 命名空间为 `/realsense`。这样启动普通仿真时，会同时生成 Husky、Velodyne 和 RealSense。

## 四、确认压缩图像话题可用于降低数据量

接入相机后，重点确认了图像数据量问题。原始 `/realsense/color/image_raw` 是未压缩图像，后续如果直接通过 MQTT 或跨进程链路传输，数据量会比较大。

运行时观察到 ROS `image_transport` 相关压缩话题已经出现，包括：

```text
/realsense/color/image_raw/compressed
/realsense/color/image_raw/compressedDepth
/realsense/color/image_raw/theora
```

因此后续如果只是需要 RGB 视频画面，建议优先使用：

```text
/realsense/color/image_raw/compressed
```

该话题类型通常为 `sensor_msgs/CompressedImage`，比原始 `sensor_msgs/Image` 更适合通过地面站链路转发。深度图和深度点云仍然较大，后续是否传输应根据地面站显示需求单独限频或按需启用。

## 五、排查并修复 Gazebo 图像格式错误

第一次启动带 RealSense 的 Gazebo 仿真时，相机插件加载了，但 Gazebo 日志中出现错误：

```text
Unsupported Gazebo ImageFormat
```

为了确认问题是否阻断相机数据发布，先查看了运行态 topic。结果显示以下 topic 都已经由 `/gazebo` 发布：

```text
/realsense/color/image_raw
/realsense/depth/image_rect_raw
/realsense/depth/color/points
```

进一步检查当前 `robot_description` 后发现，Husky 的 RealSense xacro 中将 Gazebo 图像格式写成：

```xml
<format>RGB8</format>
```

该格式会被 Gazebo 报为不支持。随后将其改为 Gazebo SDF 支持的格式：

```xml
<format>R8G8B8</format>
```

重新展开 xacro 后可以看到 `R8G8B8` 已进入 URDF。重新启动 Gazebo 后，日志中不再出现 `Unsupported Gazebo ImageFormat`，相机 topic 仍能正常发布。

这次修复改动位于 Husky 上游包内的 RealSense xacro，后续如果要保持上游包纯净，可以考虑在本地集成包中覆盖或单独维护 camera wrapper。目前先以最小改动保证仿真链路可用。

## 九、为地面站补充 Husky 重型数据仿真镜像

完成 `catkin_sim` 的 Husky + Velodyne + RealSense + `hdl_graph_slam` 仿真后，又继续把这套仿真接入当前地面站仓库，目标是做成类似 TurtleBot 仿真容器的机器人镜像，方便后续稳定生成重型数据并通过 Agent、MQTT 和 HTTP stream 链路测试地面站能力。

这里的“重型数据”主要指普通 MQTT JSON 不适合直接承载的大 payload，例如 `sensor_msgs/PointCloud2` 点云、SLAM 生成的地图点云以及后续可能扩展的图像数据。为了避免把大点云直接压到 MQTT broker 上，本次默认让点云走 Agent 已有的 HTTP stream 机制，MQTT 侧只负责发现、元信息和较轻量的状态数据。

今天新增了 Husky 专用 Agent 配置 `agent/configs/husky_001.yaml`。该配置固定机器人 ID 为 `husky_001`，HTTP stream 端口为 `8080`，宿主机访问地址为 `http://localhost:18080`。默认订阅内容围绕重型数据验证设计：

- `/velodyne_points`：Velodyne VLP-16 原始点云，使用 `http_stream`；
- `/realsense/depth/color/points`：RealSense 深度点云，使用 `http_stream`；
- `/hdl_graph_slam/map_points`：SLAM 生成的地图点云，使用 `http_stream`；
- `/hdl_graph_slam/odom`：SLAM 里程计，使用 `mqtt_binary`；
- `/tf`、`/tf_static`：坐标变换，使用 `mqtt_binary`；
- `/joint_states`：关节状态，使用 `mqtt_json`。

RealSense RGB 原始图像今天没有默认打开到 Agent 配置里。原因是当前 ROS1 Agent 对 HTTP serialized snapshot 的特殊处理主要覆盖 `sensor_msgs/PointCloud2`，图像链路后续最好单独扩展图像压缩或图像 HTTP snapshot，再决定默认订阅哪一种图像话题。

## 十一、排查 headless 容器中的 RealSense 点云发布问题

第一次用 Docker 方式启动 Husky 容器后，Velodyne 和 SLAM 相关 topic 已经正常发布，但运行态检查发现 `/realsense/depth/color/points` 只有 Agent 订阅者，没有 `/gazebo` 发布者。进一步查看日志时看到过：

```text
No protocol specified
```

同时检查 `robot_description` 可以确认 RealSense 的 Gazebo 插件已经展开进 URDF，镜像内也存在 `libgazebo_ros_openni_kinect.so`。这说明问题不是 xacro 或依赖没有进入镜像，而是 Gazebo depth camera 插件在 headless 容器中缺少可用的渲染上下文。

一个可选方案是继续沿用 TurtleBot 容器的方式，把宿主机 `DISPLAY`、`/tmp/.X11-unix` 和 `/dev/dri` 映射进容器，再通过：

```bash
xhost +si:localuser:root
```

授权 root 用户访问宿主 X11。这个方式可以解决一部分本机运行问题，但它依赖当前登录会话、宿主 X11 权限和显卡设备映射。Husky 镜像的目标是“默认启动就能稳定生成重型数据”，因此今天改为在镜像内安装 `xvfb`，并让 `husky_slam` 通过：

```bash
xvfb-run -a -s '-screen 0 1280x1024x24'
```

启动 Gazebo。这样容器不再默认依赖宿主 `DISPLAY`、X11 socket 或 `xhost` 授权，RealSense depth camera 也能在 headless 环境中获得稳定的虚拟显示和渲染上下文。

修改后重新构建镜像并重启容器，再检查 `/realsense/depth/color/points`，可以看到它已经由 `/gazebo` 发布，并且 Agent 正常订阅。
