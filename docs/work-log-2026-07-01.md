## 二、修正 Velodyne 仿真包的 ROS 版本问题

最开始在 `catkin_sim` 工作空间中执行 `catkin_make` 时失败。报错显示 `velodyne_description` 被识别为 plain CMake 包，普通 `catkin_make` 无法构建非同质工作空间。

进一步检查后发现，`src/velodyne_simulator` 当前检出的是 `ros2` 分支，包内使用的是 `ament_cmake`、`rclcpp`、`gazebo_ros` ROS2 依赖。这与当前工作空间的 ROS1 Noetic 环境不匹配。

处理方式是将该仓库切换到 ROS1 分支：

```bash
git -C src/velodyne_simulator switch -c master --track origin/master
catkin_make
```

切换后重新编译通过，工作空间能正常识别：

- `velodyne_description`
- `velodyne_simulator`
- `velodyne_gazebo_plugins`

生成的关键插件包括：

- `devel/lib/libgazebo_ros_velodyne_laser.so`
- `devel/lib/libgazebo_ros_velodyne_gpu_laser.so`

这一步解决了后续 Husky 挂载 Velodyne 的基础依赖问题。

## 三、调研现成 Docker 镜像并确定自建仿真路线

中间调研了 Docker Hub 上是否已有“搭载 Velodyne 的机器人 Gazebo 仿真”镜像。查询到的镜像中，比较直接相关的是 `bigae2/velodyne_slam_simulation-gazebo`，但该镜像较老，Docker Hub 页面说明很少，只有 `latest` 标签和截图，缺少清晰启动说明。

还查看了 `informatiklandshut/husky_gazebo_sim`，它是 Husky A200 的 Gazebo 仿真，但说明中使用的是 ZED2i 和 Ouster。Ouster 是三维激光雷达，但不是 Velodyne。该镜像体积约 6.3 GB，更适合快速参考 Husky + 3D LiDAR 仿真环境，不适合作为当前 ROS1 + Velodyne 的最终方案。

综合判断后，最终选择本地搭建：

- 底盘选择 Husky；
- 3D LiDAR 使用已经能编译通过的 `velodyne_simulator`；
- 通过本地 catkin 工作空间组织启动文件和场景。

选择 Husky 的原因是它的 ROS1 Noetic 分支已经内置 VLP16 mount xacro，车体尺寸也更适合搭载三维雷达。Jackal 也有 VLP16 mount，但车体更小；TurtleBot 更适合 2D 激光或 RGB-D 入门仿真，不适合作为 Velodyne 首选平台。

## 四、接入 Husky 并补齐运行依赖

今天拉取了 Husky 的 ROS1 Noetic 源码：

```bash
git clone -b noetic-devel https://github.com/husky/husky.git src/husky
catkin_make
```

Husky 包结构包括 `husky_description`、`husky_gazebo`、`husky_control`、`husky_navigation`、`husky_viz` 等。检查 `husky_description/urdf/accessories/` 后确认其中已有：

```text
vlp16_mount.urdf.xacro
```

这说明无需手写 Velodyne 的机械安装结构，只需要在启动时启用 Husky 的 `laser_3d_enabled` 参数。

启动过程中发现 Husky 的 description 会无条件 include 一些可选附件描述包，例如 `fath_pivot_mount_description`、`flir_camera_description`、`lms1xx`、`realsense2_description` 和 `cpr_onav_description`。这些包缺失时，即使没有启用对应相机或 2D 激光，也会导致 xacro 展开失败。

因此安装了相关 ROS Noetic 依赖：

```bash
sudo -S apt-get install -y \
  ros-noetic-cpr-onav-description \
  ros-noetic-fath-pivot-mount-description \
  ros-noetic-flir-camera-description \
  ros-noetic-lms1xx \
  ros-noetic-realsense2-description
```

随后又补齐 Husky Gazebo 启动时使用的运行节点：

```bash
sudo -S apt-get install -y \
  ros-noetic-robot-localization \
  ros-noetic-interactive-marker-twist-server \
  ros-noetic-twist-mux
```

补齐依赖后，Husky 模型可以正常 spawn 到 Gazebo 中。

## 五、新增 Husky + Velodyne 集成启动包

这个包只负责当前工作空间的集成逻辑，不改动上游 Husky 和 Velodyne 仓库。核心文件包括：

因此后续将包装 launch 改成自包含方式：由 `husky_velodyne_empty_world.launch` 直接调用 `husky.urdf.xacro`，显式传入：

- `laser_3d_parent:=top_plate_link`
- `laser_3d_topic:=/velodyne_points`

同时在同一个 launch 中加载 Husky 控制配置、启动 `robot_state_publisher`、`twist_mux`、`robot_localization`、`interactive_marker_twist_server`，并通过 `gazebo_ros/spawn_model` 生成 Husky 模型。

这样处理后，`robot_description` 中能正确展开 VLP16 和 Gazebo 插件：

```text

```

## 十、补充：接入三维激光 SLAM 链路

在 Husky + Velodyne 仿真环境可以稳定发布 `/velodyne_points` 后，继续补充了三维激光 SLAM 能力。这里的 SLAM 指机器人只依靠三维点云估计自身运动并逐步生成环境点云地图，后续可以作为地面站 RViz 点云、轨迹和地图显示的上游数据源。

本次选择 `hdl_graph_slam` 作为 SLAM 算法，并补齐了它依赖的 `ndt_omp` 和 `fast_gicp`。`ndt_omp` 和 `fast_gicp` 都是点云配准相关库，用于帮助 SLAM 前端把连续帧三维点云对齐，从而估计机器人位姿变化。

为了避免直接使用 `hdl_graph_slam` 自带 launch 造成 TF 冲突，今天在本地集成包中新增了专门面向 Husky 仿真的启动文件：

```text
/home/lab118/claudeCode_Project/catkin_sim/src/husky_velodyne_gazebo/launch/husky_hdl_graph_slam.launch
```

这个 launch 会统一启动 Gazebo、Husky、Velodyne 和 `hdl_graph_slam` 的 nodelet，包括点云预处理、scan matching odometry 和后端图优化节点。处理时特别注意没有重复发布 `base_link -> velodyne` 静态 TF，因为 Husky URDF 已经通过 `robot_state_publisher` 发布了 Velodyne 与车体之间的真实安装关系。

同时，该 launch 默认关闭 Husky 的 EKF。原因是 Husky 自身定位链路也可能发布 `odom -> base_link`，而 SLAM 前端会发布 `hdl_odom -> base_link`。如果两套定位同时抢同一个车体 TF，RViz 和后续 Bridge 侧都会更难判断哪条链路才是有效定位来源。因此当前 SLAM 启动文件使用 `hdl_odom` 作为激光里程计坐标系，并将 SLAM 输出 topic 固定为：

```text
/hdl_graph_slam/odom
/hdl_graph_slam/map_points
```

## 十一、排查并修复 hdl_graph_slam nodelet 加载问题

第一次启动 SLAM launch 时，Gazebo 和 Husky 可以起来，但 `PrefilteringNodelet` 加载失败。报错信息是：

```text
libprefiltering_nodelet.so: file too short
```

这类错误不是 launch 参数错误，而是动态库文件本身损坏或为空。检查后确认：

```bash
ls -l devel/lib/libprefiltering_nodelet.so
file devel/lib/libprefiltering_nodelet.so
```

结果显示 `libprefiltering_nodelet.so` 是 0 字节空文件，而 `libscan_matching_odometry_nodelet.so` 和 `libhdl_graph_slam_nodelet.so` 都是正常 ELF 动态库。进一步查看构建规则后发现，空文件的时间戳比对象文件新，普通 `catkin_make` 会认为目标已经是最新状态，因此不会重新链接这个库。

处理方式是强制重建该目标：

```bash
make -C build -B prefiltering_nodelet
PYTHONNOUSERSITE=1 catkin_make -j2 -l2
```

重建后再次检查：

```text
libprefiltering_nodelet.so: ELF 64-bit LSB shared object
```

随后重新启动 SLAM launch，三个 nodelet 均能正常加载，之前的 `file too short` 问题消失。
