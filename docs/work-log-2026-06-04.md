## 四、规则下发与拉取流程

今日实现并明确了编队通信规则的下发和拉取语义。

下发规则时，地面站按源机器人分组，而不是逐条规则发送。例如 `turtlebot_001` 有 3 条规则、`turtlebot_002` 有 2 条规则时，地面站会发送 2 次 `config_sync`，每台源机器人只收到属于自己的 `fleet_rules`。

拉取规则时，地面站不会依赖当前表单中选择的源机器人，而是根据当前已知在线机器人列表逐台发送 `config_query`。机器人端返回配置后，地面站只替换该源机器人对应的规则，其他源机器人的规则保持不变。

合并策略如下：

- 若响应包含 `fleet_rules`，删除表格中同一 `src_robot` 的旧规则，再追加机器人返回的新规则。
- 若响应不包含 `fleet_rules`，认为该响应与编队规则无关，不清空现有规则。
- 拉取后规则会重新写回地面站配置，保证 UI 表格和本地配置一致。

## 五、编队规则持久化

今日重点补齐了编队规则的持久化链路。

地面站端使用 `qt_frontend/config/transmit_config.yaml` 保存跨机器人视角的编队规则。新增的 `fleet_rules` 与原有 `subscriptions` 同级，规则中保留 `src_robot`，因为这是地面站 UI 分组和下发时必须依赖的信息。

地面站保存格式示例：

```yaml
fleet_rules:
  - enabled: true
    src_robot: turtlebot_001
    src_topic: /odom
    msg_type: nav_msgs/Odometry
    dst_robot: turtlebot_002
    dst_topic: /fleet/turtlebot_001/odom
    freq_limit: 10.0
    transport: mqtt_json
    frame_policy: namespace
```

下发到机器人端时，规则会转换为协议格式。机器人端收到的 `fleet_rules` 不再包含 `src_robot`，因为配置天然作用于接收该配置的源机器人：

```yaml
fleet_rules:
  - enabled: true
    src_topic: /odom
    msg_type: nav_msgs/Odometry
    targets:
      - robot_id: turtlebot_002
        dst_topic: /fleet/turtlebot_001/odom
    freq_limit: 10.0
    transport: mqtt_json
    frame_policy: namespace
```

机器人端 `agent/base_agent.py` 也补齐了写回逻辑。此前 `_save_config()` 只替换 `subscriptions`，导致机器人收到 `fleet_rules` 后运行态可以应用，但配置文件未必能正确保存。现在保存配置时会同时替换 `subscriptions` 和 `fleet_rules`，并保留 YAML 中其他顶层字段和注释。

同时修复了一个重要边界：如果地面站只下发 `fleet_rules`，机器人端不会清空已有 `subscriptions`；如果只下发 `subscriptions`，也不会清空已有 `fleet_rules`。
