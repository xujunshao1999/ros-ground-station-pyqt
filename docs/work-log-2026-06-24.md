# 工作日志 — 2026年6月24日

## 今日概览

今日围绕 ROS1 serialized 数据面迁移计划，完成了任务 1 至任务 6，并额外补充了任务 2.1，用于明确 serialized 快速路径必须受 `transport: mqtt_binary` 控制。整体目标是把高频 ROS 数据从通用 JSON 转换链路迁移到 ROS1 原生 serialized bytes，同时保留 MQTT JSON envelope 作为控制面和轻量摘要。

本轮已提交的主要变更包括协议层 `ros1_serialized_v1` encoding、Agent 端 allowlist 与 transport 双条件、Bridge 端通用 frame namespace、serialized `/tf_static` 静态广播路径、前端 `/bin` payload 保护，以及运行态配置启用 `/tf_static`、`/odom`、`/imu` 的 `mqtt_binary` 传输。

## 协议与 Agent 数据面

协议层将原先 TF 专用的 `tf_message_ros1_v1` 抽象为通用 `ros1_serialized_v1`。`protocol/binary_payloads.py` 中新增 `ENCODING_ROS1_SERIALIZED` 和 `is_ros_message_binary_supported()`，集中维护允许走 ROS1 serialized 的 `(topic, msg_type)` allowlist。当前 allowlist 覆盖 `/tf`、`/tf_static`、`/odom` 和 `/imu`，`/scan` 与 `/map` 暂不纳入 ROS1 serialized，分别继续保留现有 `laser_scan_v1` 与 `occupancy_grid_v1` 路径。

Agent 端在 `agent/ros1_agent.py` 中把动态 `/tf` 专用快速路径扩展为通用 allowlist 判断，并把 `_tf_message_seq()` 改为 `_message_seq()`，以支持普通带 `header.seq` 的消息和 `tf2_msgs/TFMessage`。后续又补充任务 2.1，明确 `ros1_serialized_v1` 只能在订阅配置为 `transport: mqtt_binary` 时启用；如果配置仍为 `mqtt_json`，即使话题命中 allowlist，也必须保留 JSON 路径。这样避免了配置语义与实际传输方式不一致。

## Bridge 与 frame namespace

Bridge 端新增针对 ROS message 对象的 `namespace_ros_message_frames()`，用于递归处理 `header.frame_id`、`child_frame_id` 和 `transforms`，避免 dict 路径和 serialized 路径各自维护一套 frame 前缀逻辑。`bridge/mqtt_ros_bridge.py` 的 serialized 发布路径现在会在启用 `namespace_tf_frames` 时统一调用该 helper。

serialized `/tf_static` 路径也补齐了静态 TF 行为。Bridge 收到 binary `/tf_static` 后，不再创建普通 ROS publisher，而是调用 `_ensure_static_tf_broadcaster()`、`_cache_robot_static_transforms()` 和 `_send_static_transforms()`，与 JSON `/tf_static` 路径保持一致。

运行态验证前发现 `bridge/bridge_config.yaml` 中 `ros.namespace_tf_frames` 原本为 `false`，这会导致地面站 TF tree 仍出现 `odom`、`base_link` 等未加机器人前缀的 frame。为满足多机器人隔离要求，本次将其改为 `true`，使 Bridge 在发布到地面站 ROS 前统一加上 `robot_id` 前缀。

## 前端 MQTT 保护

前端 `qt_frontend/mqtt_client.py` 继续忽略所有 `robot/<id>/sensor/<name>/bin` 二进制 payload，避免 Qt 主进程尝试解析高频 bytes 数据。新增测试确认 serialized `/odom` 的 JSON envelope 可以作为轻量摘要进入 UI，而 `/odom/bin` 不会触发 `sensor_data_received`。

同时将 `_IGNORED_SENSOR_TOPICS` 从仅忽略 `tf` 扩展为忽略 `tf` 和 `tf_static`。这样前端不会解析高频 TF envelope，也不会把 TF static 的 envelope 当普通 sensor 数据进入摘要面板。

MQTT envelope 验证：


ROS topic 频率验证：

```bash
timeout 12 rostopic hz /tf
timeout 12 rostopic hz /turtlebot_001/odom
timeout 12 rostopic hz /turtlebot_001/imu
timeout 12 rostopic hz /turtlebot_001/scan
```

结果：`/tf` 约 80Hz，`/turtlebot_001/odom` 约 20.5Hz，`/turtlebot_001/imu` 约 35Hz，`/turtlebot_001/scan` 约 5Hz。`timeout` 命令按预期以 124 退出，但输出中包含有效频率窗口。

frame namespace 验证：

```bash
timeout 6 rosrun tf tf_echo turtlebot_001/odom turtlebot_001/base_link
```

结果：持续输出 transform，确认 `turtlebot_001/odom` 到 `turtlebot_001/base_link` 可解析。开启 `namespace_tf_frames: true` 前，同一命令提示 `turtlebot_001/odom` 不存在，TF tree 中仍是未命名空间化的 `odom`、`base_link`、`base_scan` 等 frame；开启后该问题消失。

```bash
timeout 8 rostopic echo -n 1 /turtlebot_001/odom/header
timeout 8 rostopic echo -n 1 /turtlebot_001/imu/header
```

结果：在提升权限后，`/turtlebot_001/odom/header` 输出 `frame_id: "turtlebot_001/odom"`，`/turtlebot_001/imu/header` 输出 `frame_id: "turtlebot_001/base_footprint"`。未提升权限时，部分 `rostopic echo`、`rostopic info` 和 Python `rospy` 检查会因 sandbox 的本地 ROS XML-RPC 或日志写入限制失败；`rostopic hz` 与 `tf_echo` 仍可取到数据。
