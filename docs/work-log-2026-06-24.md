## 二、ROS1 serialized 数据面边界确认

今日首先明确了 ROS1 serialized 数据面的适用范围。该路径并不是替换整个 MQTT 协议，而是只替换高频传感器数据的 payload 表达方式。MQTT 仍然负责机器人隔离、topic 路由和 envelope 分发；真正的 ROS message bytes 通过 `<sensor-topic>/bin` 发送，JSON envelope 只保留 `encoding`、`msg_type`、`seq`、`stamp` 和 payload 大小等轻量信息。

当前纳入 ROS1 serialized allowlist 的话题包括：

- `/tf`
- `/tf_static`
- `/odom`
- `/imu`

暂不纳入的高频话题包括：

- `/scan`：继续使用现有 `laser_scan_v1` 二进制路径，后续按计划任务 7 做 A/B 对比。
- `/map`：继续使用 `occupancy_grid_v1` 加 zlib 压缩路径，不迁移到 ROS1 serialized。

这样划分的原因是 `/odom`、`/imu` 和 TF 类消息在 Bridge 侧需要尽量还原为原生 ROS message，并且 JSON 转换收益较低；而 `/scan` 和 `/map` 已经有专门的二进制压缩格式，是否切换需要单独用体积、频率和兼容性数据验证。

## 三、协议层通用 encoding 与 allowlist

协议层在 `protocol/binary_payloads.py` 中将原先 TF 专用的 `tf_message_ros1_v1` 抽象为通用 `ros1_serialized_v1`。今日新增了 `ENCODING_ROS1_SERIALIZED`，并保留 `ENCODING_TF_MESSAGE` 作为兼容别名，避免一次性改动影响既有测试和调用方。

同时新增 `is_ros_message_binary_supported()`，用于集中判断某个 `(topic, msg_type)` 是否允许走 ROS1 serialized 数据面。这个判断放在协议层，而不是散落在 Agent 或 Bridge 内部，是为了保证机器人端发布和地面站端消费对数据面边界有一致认识。

协议层测试覆盖了以下行为：

- `/tf` 和 `/tf_static` 的 `tf2_msgs/TFMessage` 可以走 `ros1_serialized_v1`。
- `/odom` 的 `nav_msgs/Odometry` 可以走 `ros1_serialized_v1`。
- `/imu` 的 `sensor_msgs/Imu` 可以走 `ros1_serialized_v1`。
- `/scan` 和 `/map` 不会被误判为 ROS1 serialized 支持话题。

## 四、Agent 发布路径从 TF 专用扩展为配置驱动

Agent 端在 `agent/ros1_agent.py` 中把原先只服务 `/tf` 的快速路径改成通用 ROS message serialized 路径。实现上直接调用 ROS message 的 `serialize()`，将原生 ROS1 bytes 发布到 MQTT binary topic，同时发布一份 JSON envelope 供前端和调试工具观察。

原先 `_tf_message_seq()` 只适用于 `tf2_msgs/TFMessage`，今日改为 `_message_seq()`。新逻辑既支持普通消息的 `header.seq`，也支持从 TFMessage 的第一条 transform header 中提取序号，用于保持 envelope 中 `seq` 字段的连续性和可观测性。

后续补充的任务 2.1 修正了一个配置语义问题：即使某个话题命中 ROS1 serialized allowlist，也只有在订阅配置明确写为 `transport: mqtt_binary` 时，Agent 才能启用 serialized 快速路径。如果配置仍为 `mqtt_json`，就必须继续走 JSON 转换路径。

这个限制很重要，因为 `transmit_config.yaml` 和机器人端配置文件是运行态行为的显式开关。否则会出现配置上看起来是 JSON 传输、实际却发出二进制 payload 的情况，后续排查会非常困难。

## 五、Bridge 反序列化、frame namespace 与 `/tf_static`

Bridge 端继续负责把 MQTT 数据重新发布到地面站本地 ROS master。今日在 `bridge/mqtt_ros_bridge.py` 中补齐了 serialized 消息的反序列化发布路径：收到 `ros1_serialized_v1` envelope 和对应 `/bin` payload 后，Bridge 根据 `msg_type` 构造 ROS message，再通过 `deserialize()` 还原消息内容。

frame namespace 是本次迁移中特别需要处理的问题。JSON 路径此前已经会对 TF frame 加机器人前缀，但 serialized 路径拿到的是 ROS message 对象，如果只做反序列化再直接发布，就会把 `odom`、`base_link`、`base_scan` 等原始 frame 泄露到地面站全局 TF tree 中。

为此今日新增 `agent/frame_utils.py` 中的 `namespace_ros_message_frames()`，用于递归处理 ROS message 对象里的 frame 字段，包括：

- `header.frame_id`
- `child_frame_id`
- `transforms`

Bridge 在 `namespace_tf_frames` 启用时统一调用这个 helper，不再只针对 dict 或 TFMessage 写专用逻辑。

`/tf_static` 也单独补齐了静态 TF 行为。Bridge 收到 serialized `/tf_static` 后，不再创建普通 publisher，而是复用静态 TF 路径，调用 `_ensure_static_tf_broadcaster()`、`_cache_robot_static_transforms()` 和 `_send_static_transforms()`。这样 `/tf_static` 仍然符合 latched/static transform 的使用语义。

运行态验证时发现 `bridge/bridge_config.yaml` 中 `ros.namespace_tf_frames` 原本为 `false`，导致地面站 TF tree 仍出现未命名空间化的 frame。今日将其改为 `true`，使 Bridge 发布到地面站 ROS 前统一补齐 `robot_id` 前缀。

## 六、前端高频数据保护

前端 `qt_frontend/mqtt_client.py` 不应该解析 ROS1 serialized 的二进制 payload。今日继续保持对 `robot/<id>/sensor/<name>/bin` 的忽略逻辑，确保 Qt 主进程不会尝试把高频 bytes 当作 JSON 处理。

同时把 `_IGNORED_SENSOR_TOPICS` 从仅忽略 `tf` 扩展为同时忽略 `tf` 和 `tf_static`。原因是 TF 类 envelope 对前端传感器摘要面板没有直接展示价值，且频率较高，继续进入 UI 信号会增加无意义负担。

对于 `/odom`，前端保留 JSON envelope 的摘要能力。也就是说：

- `/odom/bin` 会被忽略。
- `/odom` envelope 可以进入传感器摘要，用于显示话题状态和轻量元信息。
- `/tf` 和 `/tf_static` envelope 不进入普通 sensor 数据路径。

这使前端能够继续观察高频数据是否在线，同时避免承担 ROS message bytes 的解析职责。

## 七、运行态配置启用高频话题 binary 传输

今日修改了地面站和机器人端运行态配置，使 ROS1 serialized 数据面真正生效。涉及的配置文件包括：

- `qt_frontend/config/transmit_config.yaml`
- `agent/configs/turtlebot_001.yaml`
- `bridge/bridge_config.yaml`

其中 `/odom`、`/imu` 和 `/tf_static` 已切换为 `transport: mqtt_binary`。`/odom` 和 `/imu` 使用 QoS 0，降低高频数据的堆积风险；`/tf_static` 保持 QoS 1，保证静态 TF 在订阅端启动后更容易恢复。

`/scan` 当前仍保持 `mqtt_binary`，但使用的是既有 `laser_scan_v1` 路径，不属于本轮 ROS1 serialized 覆盖范围。运行态配置中 `/scan` 的 `freq_limit` 保留为 0.0，实际地面站 ROS 侧观测频率约为 5 Hz。
