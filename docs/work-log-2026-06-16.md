# 工作日志 — 2026年6月16日

## 一、今日概览

今日主要排查地面站前端 RViz 与摘要面板在运行过程中周期性卡顿的问题。最初现象表现为前端 RViz 数据每隔几秒卡一下，摘要面板中各话题的“更新”时间也会突然增大；后续在手动控制 `turtlebot_001` 运动时，RViz 中 TF 显示也出现不够流畅的情况。

排查过程中先从 `/map` 大 payload 入手，确认大地图数据会放大前端压力，但在用户手动移除 `/map` 订阅后，`LaserScan`、`TF` 等轻量数据仍然偶发卡顿。因此，今日最终判断问题主因不在 `/map`，而是前端 Qt 主线程中仍存在周期性阻塞和高频 UI 更新压力。

## 二、问题排查与证据

排查首先确认了运行链路中的几个关键事实：

- `/map` 单帧 MQTT payload 约 580 KB，ROS 侧 `/turtlebot_001/map` 单帧约 147 KB，确实会带来明显处理压力。
- 前端原先订阅 `robot/+/sensor/#` 后，会对大 payload 做完整 `json.loads()`，即使 RViz 实际使用的是 Bridge 重新发布到本地 ROS 的 topic。
- 在去掉 `/map` 订阅后，旁路 Qt/MQTT 探针显示 `/scan`、`/tf`、`/odom` 等入站消息本身较稳定，`scan` 约 5 Hz，未出现与用户观察一致的 MQTT 源头断流。
- 完整前端运行时，ROS 侧采样显示 `/tf` 约 24.7 Hz，`/turtlebot_001/scan` 约 5.0 Hz，`/turtlebot_001/odom` 约 20.9 Hz，说明 Bridge 到本地 ROS 的数据发布基本平稳。

更关键的证据来自前端退出时的堆栈：`Ctrl-C` 多次打在 Qt 主线程中的同步操作上，其中一次明确落在 `_check_ros()` 的 `subprocess.run(["rostopic", "list"], timeout=3)`。该检查每 5 秒执行一次，如果 `rostopic list` 偶尔耗时较长，会直接阻塞 Qt 主线程，导致 RViz 渲染、摘要面板刷新和其它 UI 响应一起停顿。

因此，今日将问题定位为前端主线程负载问题，而不是单纯的 ROS topic 频率或 MQTT 传输问题。

## 三、修复内容

本次修复集中在前端主线程减压。

`qt_frontend/main_window.py` 中，ROS Master 状态检查从主线程同步 `subprocess.run()` 改为后台线程执行。检查结果通过 Qt signal 回到主线程更新状态栏，并增加 `_ros_check_inflight` 标志，避免上一次检查未结束时重复启动新检查。这样可以避免 `rostopic list` 偶发变慢时卡住 RViz 渲染。

同一文件中，MQTT sensor 数据进入主窗口后不再立即同步驱动摘要面板和流量面板，而是先写入 `_pending_sensor_data`，再由 100 ms 的批处理定时器统一刷新。这减少了 `tf`、`imu`、`odom`、`joint_states`、`scan` 等高频数据对 Qt 主线程的频繁打断。

`qt_frontend/panels/sensor_summary_panel.py` 中，摘要面板内部也改为缓存最新数据并批量生成摘要。面板仍保留真实消息到达时间，用于计算 Hz、帧数和更新年龄，但摘要文本只对最新帧计算一次，避免每条高频消息都触发完整摘要构建。

`qt_frontend/mqtt_client.py` 中，针对大体积 `map` sensor payload 增加轻量摘要路径。大于阈值的 `map` 数据不再由前端完整 JSON 解析，而是生成包含 `_payload_skipped` 和 `_payload_bytes` 的轻量结构，供前端面板统计使用。

`qt_frontend/panels/traffic_monitor.py` 中，流量统计识别 `_payload_bytes`，在跳过大 payload 解析时仍能按真实 payload 大小估算带宽。

`bridge/mqtt_ros_bridge.py` 中，启动恢复订阅时保留配置里的 `qos` 字段，避免重启后恢复订阅退回默认 QoS。
