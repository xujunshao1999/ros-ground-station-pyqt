# 工作日志 — 2026年7月14日

## 一、今日概览

今天主要围绕 Husky 仿真接入地面站后的流量面板做排查和修复。当前运行链路是：Husky 容器内的 Agent 订阅本机 ROS topic，把数据通过 MQTT 发给地面站；地面站 Qt 前端订阅 `robot/+/sensor/#`，流量面板根据收到的 MQTT 消息统计各话题带宽和频率。这里的 Agent 是机器人侧进程，负责把 ROS topic 转成 MQTT 数据；Qt 前端是地面站桌面程序，负责展示机器人在线状态、传感器摘要、RViz 画面和流量统计。

今天遇到的主要问题有四类：

- Husky 配置里传输了 7 个话题，但流量面板只显示 5 个；
- `/hdl_graph_slam/odom` 和 `/realsense/color/image_raw/compressed` 配置为 `mqtt_binary`，但流量面板显示成 `mqtt_json`；
- 二进制话题在流量面板里出现重复行，例如配置行是 `hdl_graph_slam/odom`，运行态又出现 `hdl_graph_slam_odom`；
- 没有启动 TurtleBot 容器时，流量面板仍出现 `turtlebot_001/tf_static` 和 `turtlebot_002/tf_static`。
- 传输配置表和流量面板的话题列在窄侧栏中被压缩过度，长 ROS topic 只能看到开头几个字符。

整体处理结果是：流量面板会先按订阅配置创建空行，因此配置中的 7 个 Husky 话题都能看到；二进制数据的 JSON envelope 会明确携带 `transport: mqtt_binary`；前端会按 payload 中的原始 ROS topic 合并运行态数据，避免扁平 MQTT 名造成重复行；前端还会忽略 MQTT retained 的旧 sensor 消息，避免已经停止的 TurtleBot 旧 `/tf_static` 显示为实时流量。

## 二、修复流量面板只显示部分配置话题

第一轮排查时，Husky 的 `transmit_config.yaml` 和机器人端 `agent/configs/husky_001.yaml` 中都已经配置了 7 个订阅话题，包括点云、SLAM 里程计、压缩图像、TF 和关节状态。问题不在配置数量，而在流量面板的建行策略。

原来的流量面板只有收到传感器数据时才创建行。`tf` 和 `tf_static` 这类高频或静态 TF 话题在 Qt MQTT 客户端中有特殊处理：为了避免把大量 TF 内容塞进 UI，客户端会跳过完整 JSON 解析。因此这些话题即使已配置，也不会稳定触发流量行创建。

今天把流量面板调整为在收到订阅配置时先创建空行。这样即使某个话题暂时没有实时数据，或者前端只拿到轻量统计样本，用户也能看到“这个话题已配置”。空行的带宽和频率保持 0，后续收到数据后再更新。

这项改动的实际效果是：Husky 的 `/velodyne_points`、`/hdl_graph_slam/map_points`、`/hdl_graph_slam/odom`、`/realsense/color/image_raw/compressed`、`/tf`、`/tf_static`、`/joint_states` 都会在流量面板中有对应行。

## 三、修复二进制话题传输方式显示错误

第二个问题是传输方式显示。这里的 `mqtt_binary` 表示实际 ROS 数据走 MQTT 二进制 payload；同时 Agent 还会发一条 JSON envelope。envelope 是轻量说明信息，包含 topic、消息类型、编码方式、payload 大小等字段；真正的 ROS1 serialized bytes 则发到同一个 sensor topic 的 `/bin` 子 topic。`serialized` 在这里指 ROS1 原生消息序列化后的二进制字节，不再把完整 ROS message 展开成 JSON。

问题出在流量面板只消费 JSON envelope，不消费 `/bin` 的二进制 payload。旧 envelope 没写 `transport` 字段时，前端无法知道实际数据面是 `mqtt_binary`，于是落回默认 `mqtt_json` 或只依赖本地配置，导致运行态显示和配置不一致。

今天在 Agent 发布二进制数据时补上了 `transport`：

- `publish_sensor_data()` 中的传统二进制编码路径会把 envelope 标记为实际配置的 transport；
- `publish_sensor_binary_data()` 中的 ROS1 serialized 路径会把 envelope 标记为 `mqtt_binary`。

这样 `/hdl_graph_slam/odom` 和压缩图像这类话题在流量面板中会显示为 `mqtt_binary`，与配置和实际发送路径一致。

## 四、合并嵌套 ROS topic，避免重复行

后续手动测试时又看到重复话题。原因是 MQTT topic 名不能直接保留 ROS topic 开头的 `/` 和嵌套路径，在部分路径中会被转换为扁平名字。例如：

- 原始 ROS topic：`/hdl_graph_slam/odom`
- 运行态 MQTT sensor name：`hdl_graph_slam_odom`

配置行使用的是原始 ROS topic，运行态数据如果按 MQTT sensor name 建行，就会出现一条 `hdl_graph_slam/odom` 和一条 `hdl_graph_slam_odom`。压缩图像也有同类问题：原始 ROS topic 是 `/realsense/color/image_raw/compressed`，运行态扁平名可能是 `realsense_color_image_raw_compressed`。

今天把前端的数据归并规则改为优先使用 payload 里的 `topic` 字段。这个字段由 Agent 写入，表示数据对应的原始 ROS topic。流量面板和 MQTT 客户端都按这个原始 topic 归并，因此配置行和运行态统计会落到同一行，不再产生重复话题。

## 五、恢复 `/tf` 流量统计，并过滤旧 retained `/tf_static`

第三轮手动测试显示 `/tf` 流量一直是 0。这里不应该把完整 TF 数据推给摘要面板，但流量面板至少应能统计字节数和频率。今天调整为：Qt MQTT 客户端遇到 `tf` 或 `tf_static` 时仍然不解析完整 JSON，但会生成轻量样本：

- `_payload_bytes`：本次 MQTT payload 字节数；
- `_payload_skipped`：表示完整 payload 被跳过；
- `_traffic_only`：表示这条数据只用于流量统计，不进入传感器摘要面板。

主窗口批处理逻辑也同步识别 `_traffic_only`，只把这类样本送给流量面板，不送给传感器摘要面板。这样 `/tf` 能显示实时流量和频率，同时不会让 UI 因完整 TF 内容过多而变慢。

最后又排查了没有启动 TurtleBot 容器时仍出现 `turtlebot_001/tf_static`、`turtlebot_002/tf_static` 的问题。根因是 `/tf_static` 在 Agent 端使用 MQTT retained 发布。retained 消息会被 Broker 保存，新的订阅者连接后会立即收到最后一条旧消息。也就是说，这些 TurtleBot 行不是容器仍在运行，而是 Broker 里残留的旧 retained `/tf_static`。

今天在 Qt MQTT 客户端中增加过滤：对于 retained 的 sensor、sensor meta 和 sensor binary 消息，前端不把它们作为实时流量输入。这样旧机器人停止后，前端重连时不会再因为历史 retained 消息创建离线机器人流量行。Husky 当前实时 `/tf` 仍会正常统计；`/tf_static` 是静态变换，通常只发布一次或 retained，显示为 0 是合理状态。

## 六、优化表格列宽，避免长话题在窄面板中不可读

在运行态测试基本正常后，又检查了配置页和流量面板的表格显示问题。传输配置表中的“话题”列，以及流量面板中的“话题”列，在左侧区域较窄时会被压缩到只剩几个字符。虽然表格底部有横向滚动条，但原来的列宽策略使用了 `Stretch`，Qt 会优先把列压缩到当前可见宽度内，导致滚动条无法真正承担显示长 topic 的职责。

一开始用固定初始宽度做了止血，但很快发现这个方案不适合多机器人场景。不同机器人 topic 长度差异很大，例如 `/tf` 很短，而 `/realsense/color/image_raw/compressed` 很长。固定宽度要么浪费空间，要么仍然不够用。

最终改成按当前内容动态计算列宽：

- 传输配置表会按当前订阅列表中最长的 `topic` 和 `msg_type` 计算列宽；
- 新增更长话题时，话题列会自动变宽；
- 删除最长话题后，列宽会回收到当前剩余内容需要的宽度；
- 流量面板按当前 topic 集合计算话题列宽；
- 流量面板普通带宽和频率刷新不参与列宽计算，避免每次统计刷新导致列宽抖动；
- 两个表都保留横向滚动条，窄侧栏中内容溢出时通过横向滚动查看完整话题名。

这项调整主要改善实际操作体验：用户不需要为了看完整 topic 手动拉宽左侧区域，也不需要在多个机器人、长短 topic 混合时反复拖动列宽。
