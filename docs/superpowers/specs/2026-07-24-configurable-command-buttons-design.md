# 可配置模式命令按钮设计

## 背景

地面站左下角的“模式控制”目前固定提供“手动、自动、停止、急停、回家”按钮。除“停止”会在 ROS1 Agent 侧发布零速度外，“手动”和“自动”只修改 Agent 内部状态，“回家”尚未接入 `move_base`，这些固定按钮对 Turtlebot、Husky 以及多机探索算法缺少通用意义。

本次设计将模式控制区改为 4 个固定位置的可配置命令按钮。每个按钮用于向点击时全部在线机器人发布同一条 ROS 消息。顶部工具栏现有“全部急停”继续作为固定安全入口，模式控制区不再重复提供急停按钮。

## 目标

- 模式控制区固定显示 4 个命令按钮，不提供新增、删除或排序。
- 用户可为每个位置配置显示文字、ROS 话题、消息类型和消息参数。
- 话题优先从在线机器人发现结果中选择，消息类型随话题自动填充，同时保留手工输入。
- 根据消息结构递归生成 Qt 参数表单，并提供完整 JSON 高级编辑模式。
- 每次点击均向当时全部在线机器人逐台发送，并汇总各机器人的执行确认。
- 支持机器人 ROS 环境中已经安装并完成 `source` 的 ROS1 自定义消息类型。
- 配置保存在地面站本地，应用重启后恢复。

## 非目标

- 本期不支持按钮新增、删除、拖拽排序、分组或超过 4 个位置。
- 本期不支持选择单台机器人、临时勾选多台机器人或固定机器人子集。
- 本期不让地面站直接加载 ROS 消息 Python 类；ROS 消息实例仅在机器人 Agent 中构造。
- 本期不替代顶部工具栏的“全部急停”，也不允许把普通命令按钮提升为急停入口。
- 本期不解决自定义传感器消息在地面站本地 roscore 的重新发布依赖；该链路仍要求地面站 ROS 环境安装相应消息包。

## 术语与执行约定

- **命令按钮位置（slot）**：模式控制区固定的 4 个位置，内部标识为 `slot_1` 至 `slot_4`。位置标识用于加载配置，不是 ROS 消息字段。
- **在线机器人**：`RobotListPanel` 中根据状态或发现响应判定为在线、且尚未超过心跳超时的机器人。点击按钮时重新取得在线列表；之后上线的机器人不会补发本次命令。
- **ROS 话题（topic）**：机器人 Agent 最终发布消息的 ROS1 话题，例如 `/exploration/control`。文档中的话题名称均为示例，不规定算法必须采用该名称。
- **消息类型（msg_type）**：ROS1 的 `package/Message` 类型名，例如 `my_pkg/ExplorationControl`。自定义类型必须在每台目标机器人的 ROS 环境中可解析。
- **消息参数（data）**：与消息字段结构一致的 JSON object。Agent 使用现有 `agent.dict_to_ros_msg.dict_to_ros_msg()` 将其递归转换为 ROS 消息对象。
- **消息结构（schema）**：Agent 从 ROS 消息类的 `__slots__` 和 `_slot_types` 递归解析出的字段树，供地面站生成参数表单。它不是新的 ROS `.msg` 定义文件。
- **结构化表单**：地面站根据 schema 为基础字段、嵌套消息、时间和数组生成的 Qt 控件集合。
- **JSON 高级编辑**：直接编辑完整 `data` object 的模式。它与结构化表单共享同一份内存数据，切换时进行双向转换和校验。
- **未经在线校验**：用户手工填写了话题、类型或 JSON，但当前没有 Agent 成功返回对应 schema。该配置可以保存和发送，但界面必须明确显示此状态，最终以目标 Agent 的转换结果为准。
- **执行 ID（exec_id）**：一次按钮点击生成的唯一标识。同一次点击向多台机器人发送时共用该 ID，前端使用 `(exec_id, robot_id)` 区分并汇总确认。
- **命令确认（cmd_ack）**：Agent 执行命令后通过现有确认 topic 返回的结果，包含 `exec_id`、`result` 和 `message`。

## 已确认的产品行为

### 模式控制区

模式控制组标题右侧增加齿轮图标按钮。组内显示“发送目标：全部在线机器人（当前 N 台）”，下方采用 2×2 网格展示 4 个固定位置。

配置文件不存在、对应位置缺失或配置无效时，按钮文字显示“未配置”并禁用。只有保存了有效的显示文字、话题、消息类型和 object 类型参数后，该按钮才启用。

模式控制区删除“急停”按钮。顶部工具栏“全部急停”保持现有确认对话框和“零速度 + 停止模式”双指令行为，始终作为独立安全入口。

### 设置窗口

点击齿轮打开模态设置窗口。左侧列出 4 个固定位置，右侧编辑当前位置：

1. “显示字样”使用单行文本输入。
2. “ROS 话题”使用可编辑下拉框。下拉项来自在线机器人发现结果，手工话题必须通过现有 ROS 话题格式校验。
3. “消息类型”在选择已发现话题后自动填入，也允许手工输入合法的 `package/Message` 名称。
4. 选择或修改消息类型后，前端向一台代表机器人查询 schema。代表机器人取当前在线机器人 ID 排序后的第一台；项目按同构机器人集群处理，不比较全部机器人的 schema。
5. 参数区域提供“结构化表单”和“JSON 高级编辑”两个标签。两种模式编辑同一份 `data`。
6. 保存按钮一次性保存 4 个位置；单个位置校验失败时保留窗口并定位到该位置，不写入部分配置。

如果没有在线机器人，设置窗口仍可使用缓存的 schema 或手工填写类型和 JSON。此时显示“未经在线校验”，不假装参数已由机器人验证。

### 结构化表单

Agent 返回的 schema 节点至少包含字段名、ROS 类型、是否为数组、固定数组长度以及嵌套字段。前端按以下规则渲染：

- 字符串：`QLineEdit`。
- 布尔值：`QCheckBox`。
- 整数和浮点数：带类型范围或精度约束的数值输入控件。
- `time` 和 `duration`：`secs`、`nsecs` 两个数值字段。
- 嵌套消息：带字段路径标题的可折叠分组，递归生成子字段。
- 数组和字节数组：在结构化表单内使用受校验的 JSON 数组编辑控件；完整消息仍可切换到 JSON 高级编辑。

schema 解析必须检测循环引用并限制最大嵌套深度，避免异常消息定义导致无限递归。无法渲染的字段不应被静默忽略，而应提示用户改用 JSON 高级编辑。

JSON 切换回结构化表单前必须完成 JSON 语法、顶层 object 类型和已知 schema 字段类型校验。校验失败时留在 JSON 标签并展示具体字段路径。结构化表单修改后应即时更新 JSON 表示。

## 配置持久化

新增 `qt_frontend/config/command_buttons.yaml`，使用带版本号的独立配置，避免把运行时按钮数据混入主程序配置。建议结构如下：

```yaml
version: 1
slots:
  slot_1:
    label: "开始探索"
    topic: "/exploration/control"
    msg_type: "my_pkg/ExplorationControl"
    data:
      command: "start"
    schema:
      type: "my_pkg/ExplorationControl"
      fields: []
    schema_status: "verified"
  slot_2: null
  slot_3: null
  slot_4: null
```

schema 快照随按钮配置缓存，使机器人离线时仍可重新打开结构化表单。再次取得在线 schema 后刷新缓存；即使缓存存在，Agent 在每次执行时仍按其本地实际消息类重新转换，缓存不作为执行依据。

保存时先写入同目录临时文件，完成 YAML 序列化和回读校验后再原子替换目标文件。配置缺失时使用 4 个未配置位置；YAML 无法解析、版本不支持或顶层结构错误时不加载半有效内容，回退为未配置状态并在界面显示警告。

## 协议扩展

### 消息结构查询

在 `protocol/topics.py` 集中增加目标机器人专用的 schema 查询与响应 topic，避免让所有 Agent 处理同一查询：

```text
station/{robot_id}/message_schema/query
station/{robot_id}/message_schema/response
```

查询消息使用新的 `message_schema_query` 类型：

```json
{
  "type": "message_schema_query",
  "dst": "turtlebot_001",
  "data": {
    "request_id": "8ec1d94a",
    "msg_type": "my_pkg/ExplorationControl"
  }
}
```

响应使用 `message_schema_response` 类型，携带相同 `request_id`、`msg_type`、`result`、递归 `schema` 或明确的 `error`。前端只接受 robot ID、request ID 和类型均与当前请求匹配的响应，过期响应不能覆盖用户之后选择的新类型。

Agent 只解析本地已经安装的消息类，不接收或执行来自地面站的 Python 代码。未知类型、循环引用、超出深度或结构过大均返回错误响应。

### 自定义命令

继续使用现有 `cmd` 消息和 `action: custom`，将参数统一为：

```json
{
  "action": "custom",
  "params": {
    "topic": "/exploration/control",
    "msg_type": "my_pkg/ExplorationControl",
    "data": {
      "command": "start"
    }
  },
  "exec_id": "23a405c9e8e1"
}
```

这同时修正文档与当前 ROS1 Agent 实现之间的差异：当前实现把自定义参数 JSON 序列化为 `std_msgs/String`，新实现必须使用 `msg_type` 动态加载消息类、调用 `dict_to_ros_msg(data, msg_type)`，再发布真实类型的 ROS 消息。

现有 `dict_to_ros_msg()` 对未知字段采用限频告警以兼容传感器桥接。本功能为它增加默认关闭的严格模式，保持原调用方行为不变；custom 命令必须启用严格模式，使未知字段、错误嵌套结构和无法转换的值抛出带字段路径的异常，再由 Agent 转成失败确认。

ROS1 Agent 按 topic 缓存 Publisher 及其 `msg_type`。同一 topic 再次使用相同类型时复用 Publisher；若后续命令把该 topic 改为不同类型，Agent 先注销自己缓存的旧 Publisher，再创建新类型 Publisher。创建或发布失败时返回错误确认，不保留不可用缓存，也不得把错误类型发布到旧 Publisher。

Mock Agent 不依赖 ROS，但需要验证 `topic`、`msg_type` 和 `data` 的基本结构，并以成功或失败确认模拟协议行为。

## 发送与确认汇总

点击已配置按钮时，前端按以下顺序执行：

1. 读取按钮配置的不可变快照，避免发送过程中设置窗口修改参数。
2. 从 `RobotListPanel.get_online_robots()` 获取当时在线机器人并排序。
3. 在线列表为空时不发送，提示“当前没有在线机器人”。
4. 生成一个新的 `exec_id`，向每台在线机器人各发送一条内容相同、目标不同的 `cmd`。
5. 记录预期机器人集合，按 `(exec_id, robot_id)` 接收 `cmd_ack`。
6. 5 秒后将尚未确认的机器人标记为“响应超时”，不自动重发。
7. 在模式控制区或状态提示中显示“发送 N 台：成功 X、失败 Y、超时 Z”，并允许查看失败机器人和 Agent 返回的错误文本。

不同按钮的连续点击生成不同 `exec_id`，确认状态互不覆盖。重复、未知或过期确认只记录调试日志，不改变已完成批次结果。

## 错误处理

- 话题、消息类型、参数或配置版本无效：拒绝保存该批配置。
- 手工配置未取得 schema：允许保存，但显著标记“未经在线校验”。
- JSON 语法错误或顶层不是 object：拒绝保存和发送。
- Agent 找不到消息类型：返回错误确认，说明目标机器人需要安装并 `source` 对应消息包。
- 字段不存在、嵌套结构错误或值无法转换：返回包含字段路径的错误确认。
- ROS Publisher 创建或发布异常：捕获异常并返回错误确认，不使 Agent 主循环退出。
- 部分机器人失败：保留其余机器人的成功结果，不进行全体回滚或自动补发。
- MQTT 断开：不尝试发送，并提示连接状态错误。

## 组件边界

- `qt_frontend/panels/command_panel.py`：展示 4 个位置、打开设置窗口、维护单次发送的确认汇总；不直接发布 MQTT。
- 新的按钮配置模块：定义配置数据类、YAML 读写、字段校验和 schema/data 转换逻辑，避免继续扩大 `CommandPanel`。
- 新的 Qt 设置对话框模块：负责 4 个位置导航、话题选择、递归表单和 JSON 编辑。
- `qt_frontend/main_window.py`：提供在线机器人集合，协调批量发送和 MQTT 信号连接。
- `qt_frontend/mqtt_client.py`：发送 schema 查询和命令，解析 schema 响应并保留 `exec_id`。
- `protocol/`：定义新增消息类型、数据结构和所有 MQTT topic helper，不依赖 ROS、Qt 或 MQTT 客户端。
- `agent/base_agent.py`：订阅和分发 schema 查询，生成标准响应。
- `agent/ros1_agent.py`：解析本地 ROS 消息结构，并将 custom 命令转换为真实 ROS 消息后发布。
- `agent/mock_agent.py`：提供无 ROS 环境可测试的 schema 示例和 custom 命令校验。

## 测试与验证范围

### 无 ROS pytest

- 配置文件缺失、4 个位置部分配置、完整配置、损坏 YAML 和不支持版本。
- 配置原子保存以及保存失败时不覆盖已有有效文件。
- schema 基础字段、嵌套字段、时间、数组、循环和深度限制。
- schema 到参数默认值、结构化表单到 JSON、JSON 到结构化表单及字段路径错误。
- 话题选择自动填充消息类型；过期 schema 响应不覆盖当前选择。
- 无在线机器人、全部在线机器人发送、同批共享 `exec_id`、不同批次 ID 隔离。
- 成功、部分失败、重复确认、未知确认和 5 秒超时汇总。
- Mock Agent 对 custom 命令的成功与失败确认。
- ROS1 Agent 使用 fake ROS 消息类验证 Publisher 缓存、真实类型构造、转换错误和发布异常。
- 顶部全部急停行为不回归，模式控制区不再包含急停按钮。

运行命令：

```bash
QT_QPA_PLATFORM=offscreen python3 -m pytest tests/ -v
ruff check protocol/ agent/ qt_frontend/ tests/
```

实际完成时只对本次修改的手写 Python 文件执行 `ruff check`；上面的目录级命令用于设计阶段说明覆盖范围，不把全仓历史基线当作完成判据。

### ROS Noetic 集成验证

至少准备一个工作空间内已安装自定义消息包的 ROS1 Agent，验证：

1. 地面站能取得自定义消息的递归 schema。
2. 表单和 JSON 两种方式生成的参数均能发布为真实自定义消息类型。
3. `rostopic echo` 能观察到字段值正确。
4. 一台机器人缺少消息包时，该机器人返回失败，其他机器人仍成功。
5. 多台同构机器人在线时，一次点击会向全部在线机器人发布且确认汇总正确。

Mock Agent 和无 ROS pytest 通过不等同于真实自定义消息链路通过。若执行环境缺少 ROS Noetic、自定义消息包、MQTT Broker 或多机器人容器，最终回复必须明确列出未覆盖风险。

## 兼容与迁移

- 不读取旧模式按钮硬编码作为默认配置。首次启动或没有新配置文件时，4 个位置全部为“未配置”。
- 现有速度方向控制保持单机器人操作方式，不在本期随模式按钮改为全体发送。
- 顶部全部急停、机器人列表、话题传输配置和编队通信配置保持原有入口与协议。
- `custom` 命令从固定 `std_msgs/String` 改为真实 `msg_type` 发布属于行为修正；依赖旧 String 包装行为的外部调用方需要改为显式配置 `std_msgs/String` 和 `data: {data: "..."}`。

## 完成判据

- 用户能配置并持久化 4 个按钮，重启后正确恢复。
- 已发现话题能自动填充消息类型，并能取得嵌套自定义消息 schema。
- 结构化表单与 JSON 高级编辑模式对同一参数数据保持一致。
- 点击按钮只向点击时全部在线机器人发送，并正确展示成功、失败和超时汇总。
- ROS1 Agent 发布的消息类型与配置的 `msg_type` 一致，而不是统一包装为 String。
- 配置、schema、发送和错误路径均有聚焦自动化测试。
- 顶部全部急停继续可用，模式控制区不再出现重复急停入口。
