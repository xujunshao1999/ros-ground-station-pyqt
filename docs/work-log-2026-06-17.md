# 工作日志 — 2026年6月17日

## 今日概览

围绕 `mqtt_json` 与 `mqtt_binary` 的实际生效情况完成排查和改进。排查确认，原实现中 `/scan` 与 `/map` 虽在 `transmit_config.yaml` 和机器人端 `config.yaml` 中标记为 `mqtt_binary`，但 Agent 发布端仍主要按消息类型 registry 选择层级，并将 MEDIUM 数据序列化为 JSON bytes。Bridge 与前端也都按 JSON payload 处理传感器数据，因此 `mqtt_binary` 在运行态没有体现真实二进制传输。

本次改动将第一阶段范围收敛到二维激光 `sensor_msgs/LaserScan` 和二维栅格地图 `nav_msgs/OccupancyGrid`，建立“JSON envelope + MQTT binary payload”的数据通道。三维点云 `PointCloud2` 暂未接入，只保留后续扩展方向。

## 问题排查与修复

新增 `protocol/binary_payloads.py`，集中处理二进制传感器 payload 的编码与解码。`LaserScan` 使用 `laser_scan_v1`，将 `ranges` 与 `intensities` 编码为 little-endian `float32`；`OccupancyGrid` 使用 `occupancy_grid_v1`，将 `data` 编码为 `int8` 原始数组并使用 `zlib` 压缩。Envelope 保留 `topic`、`msg_type`、`encoding`、`payload_format`、`payload_size`、`compression` 和必要 meta 信息。

Agent 端在 `BaseAgent.publish_sensor_data()` 中读取运行态订阅的 `transport` 字段。订阅配置为 `mqtt_binary` 且消息类型受支持时，Agent 会向 `robot/<id>/sensor/<name>` 发布 JSON envelope，并向 `robot/<id>/sensor/<name>/bin` 发布真实二进制 payload；其他类型或 `mqtt_json` 仍保持旧 JSON 路径。运行态订阅信息同步补充 `transport`，避免配置变更只保存不生效。

Bridge 端新增 binary envelope 缓存与 `/bin` payload 处理逻辑。收到 envelope 后按 `(robot_id, sensor_name)` 缓存，收到对应二进制 payload 后通过协议模块解码为 ROS 字段字典，再复用原有 `dict_to_ros_msg()` 发布到本地 ROS topic。旧 JSON sensor payload 保持兼容。

前端 MQTT 客户端新增 `sensor_binary` topic 保护逻辑，收到 `robot/<id>/sensor/<name>/bin` 时直接忽略，不再尝试 `json.loads()` 或 `Message.from_json()`，避免大二进制 payload 进入 Qt UI 路径。

## 功能完善

`protocol/topics.py` 新增 `robot_sensor_binary()` 与 `all_robot_sensor_binary()`，并扩展 `parse_robot_topic()`，使 `robot/<id>/sensor/<name>/bin` 被解析为 `sensor_binary`，普通 sensor topic 与 `sensor_meta` topic 不受影响。

## RViz 流畅度排查与修复

在用户启动前端和 Bridge 后，继续排查 RViz 中 LaserScan 显示不流畅的问题。对照验证显示，容器内原始 `/scan` 为稳定 5Hz，地面站侧 `/turtlebot_001/scan` 在 QoS 调整后也恢复到约 5Hz。随后检查运行日志发现 `logs/mosquitto.log` 接近 5GB，`logs/mosquitto-start.log` 超过 2GB，日志内容为 Mosquitto 对每条 sensor publish 的 `Received PUBLISH`、`Sending PUBLISH` 与 `PUBACK` 记录。

根因是本地 broker 默认配置启用了 `log_type information` 和 `log_dest stdout`，同时 `broker/start.sh`、`broker/start.bat` 以 `-v` 启动 Mosquitto。二进制 LaserScan 每帧拆成 envelope 与 `/bin` 两条 MQTT 消息后，逐条消息日志写入被进一步放大，造成明显磁盘 I/O 压力，进而影响前端和 RViz 的主观流畅度。

已调整 broker 默认运行策略：`broker/mosquitto.conf` 去掉 `log_type information` 与 `log_dest stdout`，仅保留 `error`、`warning`、`notice`；`broker/start.sh` 与 `broker/start.bat` 去掉 `-v`；`docker/mosquitto.conf` 同步去掉 `log_type information`。同时 `broker/start.sh` 增加 `mkdir -p "$PROJECT_ROOT/data"`，避免启用 persistence 时因 `data/` 目录不存在导致退出保存数据库失败。

已新增 `tests/test_broker_config.py`，覆盖默认 Mosquitto 配置不启用逐条消息日志、启动脚本不强制 verbose，以及 Linux 启动脚本会创建 persistence 目录。执行结果：

## 摘要面板话题类型误判修复

用户继续反馈前端摘要面板中 `/map` 和 `/scan` 的话题类型会跳变为 `sensor_msgs/Image`。排查确认 Bridge 本地 ROS 发布不是根因，问题发生在前端摘要面板的 MQTT 数据路径。二进制传输后，前端收到的 sensor topic 是 JSON envelope，例如 `/scan` envelope 包含 `msg_type=sensor_msgs/LaserScan` 和 `encoding=laser_scan_v1`，`/map` envelope 包含 `msg_type=nav_msgs/OccupancyGrid` 和 `encoding=occupancy_grid_v1`。摘要面板原先只识别 `_msg_type`，未读取协议 envelope 的 `msg_type`，随后按 `encoding` 字段启发式推断为 `sensor_msgs/Image`，导致 UI 类型显示来回变化。

已修复 `qt_frontend/panels/sensor_summary_panel.py`：`infer_msg_type()` 现在在 `_msg_type` 之后优先读取协议标准字段 `msg_type`，再进入 `ranges`、`encoding` 等字段启发式推断。这样 binary envelope 会保留真实 ROS 类型，不会被 `encoding` 字段误判为图像。
