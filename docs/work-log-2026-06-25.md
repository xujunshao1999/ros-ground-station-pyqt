## 一、今日概览

今天开始做点云数据传输链路的第一阶段改造。背景是：`sensor_msgs/PointCloud2` 这类点云消息体积比较大，如果直接把完整数据塞进 MQTT 消息里传，会给 broker、Bridge 和前端都带来比较大的压力，也容易出现消息堆积、延迟变高或 UI 误解析的问题。

今天没有直接把整条点云链路一次性接完，而是先把基础能力补齐：准备可测试的点云数据、扩展协议字段、把 `PointCloud2` 标记为重型数据，并让机器人端 Agent 具备“缓存大数据、只通过 MQTT 发送取数提示”的能力。

这里的“HTTP snapshot”可以理解为“最新一帧数据快照”：Agent 本地只保存某个点云话题最新一帧二进制数据，Bridge 后续需要时通过 HTTP 去取。MQTT 不再传完整点云，只传一小段说明信息，例如这个数据在哪里取、是什么类型、有多大、属于哪个 frame。

## 二、先准备可测试的点云数据

点云链路后面会依赖 ROS 的 `PointCloud2` 消息，但单元测试环境不一定有完整 ROS 环境。如果每个测试都依赖 roscore 或真实 `sensor_msgs`，开发和回归都会很不方便。

所以今天先新增了 `agent/mock_pointcloud2_data.py`，用纯 Python 生成一份稳定的假点云数据。它的作用是让后续 Agent、ROS1 Agent 和 Bridge 的测试都能复用同一份数据，不需要每次都启动 ROS。

这个工具做了几件事：

- 生成一组固定的 XYZ 点，方便测试判断数据有没有变化。
- 构造类似 `PointCloud2` 的字典，里面包含 `header`、`fields`、`point_step`、`row_step` 和原始二进制 `data`。
- 提供一个 `FakePointCloud2Message`，模拟 ROS message 常见的 `header`、`serialize()` 和 `deserialize()` 行为。

这部分只是测试工具，不会替代真实 ROS 点云消息。真正接入机器人点云时，后续仍然会使用 ROS message 自己的序列化能力。

## 三、扩展点云取数说明信息

第二项工作是扩展 `SensorMetaData`。这里的 `meta` 可以理解成“取数说明”或“数据说明卡片”，它不是点云本体，而是告诉 Bridge：

- 这个数据对应哪个 ROS topic；
- 这个数据是什么消息类型；
- 应该通过哪个 HTTP 地址去取；
- 数据大小是多少；
- 原始消息序号、时间戳和 frame 是什么；
- 数据编码格式是什么。

旧的 `SensorMetaData` 字段比较少，只能表达 topic、消息类型、传输方式、URL 和大小。对于后续 Bridge 拉取点云并重新发布到本地 ROS 来说，这些信息不够。因此今天新增了：

- `seq`：原始消息序号。
- `stamp`：原始消息时间戳。
- `frame_id`：原始 frame。
- `encoding`：当前使用 `ros1_serialized_v1`，表示这是 ROS1 原生序列化数据。
- `payload_format`：当前使用 `ros1_serialized`，表示 HTTP 中返回的是 ROS1 序列化后的二进制内容。
- `payload_size`：HTTP 中实际可取到的数据大小。

这样 Bridge 后续拿到 MQTT 上的 `sensor_meta` 后，就能知道该去哪里取点云、应该按什么格式还原、还原后该如何补齐 frame namespace。

## 四、把 PointCloud2 标记为重型数据

第三项工作是调整话题类型注册表。此前 `sensor_msgs/PointCloud2` 被归为中等数据，默认更接近 MQTT 二进制传输。今天将它改为重型数据，默认传输方式变为 `http_stream`，默认频率限制调整为 `2 Hz`。

这个调整的含义是：系统看到 `sensor_msgs/PointCloud2` 时，会把它当作大体积数据处理，不再默认走普通 MQTT payload 路径。这样后续订阅点云时，Agent 和 Bridge 可以按重型数据策略处理。

旧版 `sensor_msgs/PointCloud` 这次没有一起迁移，仍然保留为中等数据。原因是第一版计划只验证 `PointCloud2`，旧点云类型是否需要走同一条链路，后面再单独判断。

## 五、Agent 侧支持“缓存大数据，发送取数提示”

第四项工作是在 `BaseAgent` 中补齐重型数据发送能力。这里的核心变化是：Agent 不直接把完整点云发到 MQTT，而是把点云二进制内容存在本地内存里，并通过 HTTP endpoint 暴露出来；MQTT 只发送一条很小的取数提示。

今天新增了两个配置字段：

- `stream_public_host`：Bridge 能访问到的 Agent HTTP 地址所在主机。
- `stream_base_url`：如果部署环境比较特殊，可以直接指定完整 HTTP 基础地址。

为什么需要这两个配置？因为 Docker 或多机部署时，Agent 自己看到的本机 IP 不一定是 Bridge 能访问的地址。如果 MQTT 里发了一个容器内部地址，Bridge 就会拉取失败。因此需要允许配置一个对 Bridge 可达的地址。

今天新增的 `publish_heavy_snapshot_data()` 做了这些事：

- 确认这个 ROS topic 当前确实被订阅。
- 根据限频配置判断这一帧是否可以发送。
- 把点云二进制内容缓存到 `_stream_data`。
- 启动 HTTP stream server，供 Bridge 后续拉取。
- 生成一条 `sensor_meta` 消息，里面包含取数 URL、消息类型、数据大小、序号、时间戳和 frame。
- 把这条说明信息发布到 `robot/<robot_id>/sensor/<sensor_name>/meta`。

实现时还修正了一个细节：MQTT topic 里不能直接使用 `/velodyne_points` 这种带开头斜杠的 ROS topic，否则会生成多余斜杠。实际发布时会把它转换成 `velodyne_points`，与协议文档中定义的 sensor name 规则一致。
