## 二、修复 `/map` OccupancyGrid 无数据问题

### 2.1 问题背景

5月9日工作日志中记录过 `/map` 未完成项：MQTT 侧可以收到 `robot/turtlebot_001/sensor/map`，Bridge 侧也能看到 `/turtlebot_001/map` publisher，但 ROS 侧执行：

```bash
rostopic echo /turtlebot_001/map
```

一直没有实际消息输出。

当时已确认：

- MQTT payload 约 574KB。
- 地图尺寸为 `384 x 384`。
- `/turtlebot_001/map` 类型为 `nav_msgs/OccupancyGrid`。
- `/mqtt_ros_bridge` 已经作为 publisher 注册。
- `/odom`、`/scan`、`/imu`、`/tf`、`/joint_states` 等其他话题正常。

因此问题集中在大消息转换、ROS 序列化或发布链路上。

### 2.2 排查过程

用户已启动 `robot-turtlebot-001` 容器。宿主机启动地面站链路：

```bash
./qt_frontend/scripts/start.sh
```

启动检查项均通过，包括 roscore、Mosquitto、Bridge、Qt 前端、`transmit_config.yaml` 和 `librviz_widget.so`。

随后验证 MQTT 侧地图数据：

```bash
timeout 8 mosquitto_sub -h localhost -t 'robot/+/sensor/map' -C 1 | head -c 300
```

能看到 `header`、`info`、`width=384`、`height=384` 等字段，说明 Agent 端订阅 `/map`、序列化和 MQTT publish 正常。

继续验证 ROS topic：

```bash
source /opt/ros/noetic/setup.bash
rostopic info /turtlebot_001/map
```

输出显示：

```text
Type: nav_msgs/OccupancyGrid

Publishers:
 * /mqtt_ros_bridge
```

但执行：

```bash
timeout 8 rostopic echo -n 1 /turtlebot_001/map/header
timeout 12 rostopic hz /turtlebot_001/map
```

仍无有效输出。说明 topic 注册成功，但消息没有真正发布出去。

### 2.3 诊断增强

为了定位 Bridge 内部问题，临时增强了 `bridge/mqtt_ros_bridge.py`：

- 对大于 256KB 的 payload 记录 JSON decode、ROS message convert、publish 耗时。
- 记录 publisher 当前连接数。
- 新增 `_wait_for_publisher_connection()`，在 typed publisher 首次创建后短暂等待 subscriber 连接，降低低频大消息首帧丢失概率。

这些增强最终保留为 debug 级诊断能力，不改变协议和消息内容。

### 2.4 根因定位

用真实 MQTT map payload 直接测试转换和序列化：

```python
data = json.loads(payload.decode("utf-8"))
msg_type = data.pop("_msg_type")
msg = dict_to_ros_msg(data, msg_type)
buf = io.BytesIO()
msg.serialize(buf)
```

修复前输出显示：

```text
msg_type nav_msgs/OccupancyGrid
data len 147456
sample [-1, -1, -1, -1, -1, -1, -1, -1]
ros data type <class 'bytes'>
sample [255, 255, 255, 255, 255, 255, 255, 255]
serialize failed SerializationError field data must be a list or tuple type. Only uint8[] can be a string
```

根因是 `nav_msgs/OccupancyGrid.data` 类型为 `int8[]`，地图未知区域使用 `-1` 表示。原 `dict_to_ros_msg.py` 把 `int8[]` 和 `uint8[]` 都转成了 `bytes`：

- `int8[]` 中的 `-1` 被转换成 `255`。
- ROS `genpy` 只允许 `uint8[]` 使用 bytes/string 快捷表示。
- `int8[]` 必须保持 `list` 或 `tuple`。

因此 Bridge 调用 `pub.publish(ros_msg)` 时实际在 ROS 序列化阶段失败，导致 publisher 存在但无消息输出。

### 2.5 修复内容

修改 `bridge/dict_to_ros_msg.py` 的数组转换逻辑：

```python
# uint8[] / char[] / byte[] may be represented as bytes in genpy.
# int8[] must remain a list/tuple because signed values such as
# OccupancyGrid.data can contain -1.
if base_type in ("uint8", "char", "byte") and fixed_length is None:
    return bytes(b & 0xFF for b in val)
```

修复后：

- `uint8[]`、`char[]`、`byte[]` 仍保持 bytes 优化。
- `int8[]` 保持 `list[int]`，能正确表示 `-1`。
- `OccupancyGrid.data` 不再丢失符号。

新增测试覆盖：

```python
def test_uint8_array_to_bytes(self):
    result = _convert_value([0, 1, 255, 128], "uint8[]")
    assert isinstance(result, bytes)

def test_int8_array_stays_list(self):
    result = _convert_value([-1, 0, 100], "int8[]")
    assert result == [-1, 0, 100]
```

## 三、完善话题配置传输闭环

### 3.1 初始问题

话题配置页原本只有 UI，缺少实际行为：

- 添加话题不会生成 `topic_request`。
- 删除话题不会通知机器人取消订阅。
- “下发配置到机器人”没有发布 `config_sync`。
- “从机器人拉取话题”没有发布 `config_query`。
- 机器人返回 `topic_resp` 或 `config_response` 后，表格状态不会更新。
- Agent 收到单条 `topic_request` 后不会写入持久配置。
- Agent 的 `config_sync` 只会新增缺失订阅，不会删除地面站已移除的话题。

本次只处理地面站和机器人端的话题配置传输闭环，机器人间编队功能仍后置。

### 3.2 前端 TopicConfigPanel 功能

在 `qt_frontend/panels/topic_config_panel.py` 中补齐了面板行为：

- `SubscriptionEntry.to_dict()` / `from_dict()`：负责 UI 订阅项和协议字典的转换。
- `topic_request_requested(robot_id, data)`：添加/删除话题时发送单条订阅请求。
- `config_sync_requested(robot_id, data)`：下发完整订阅配置。
- `config_query_requested(robot_id)`：从机器人拉取当前配置。
- `on_topic_response(robot_id, data)`：根据机器人返回结果更新话题状态。
- `on_config_response(robot_id, data)`：加载机器人端当前 `subscriptions`。
- `on_robot_list_changed(robot_ids)`：同步在线机器人列表。

按钮行为调整为：

- “确认”：添加或覆盖当前 topic，并发送 `subscribe topic_request`。
- “删除”：删除选中行，并发送 `unsubscribe topic_request`。
- “从机器人拉取话题”：发送 `config_query`。
- “下发配置到机器人”：发送 `config_sync` 并保存地面站本地配置。
- “保存配置”：只保存地面站本地 `transmit_config.yaml`。

### 3.3 MainWindow 和 MQTT 接线

在 `qt_frontend/main_window.py` 中接通：

- `topic_response_received -> TopicConfigPanel.on_topic_response`
- `config_response_received -> TopicConfigPanel.on_config_response`
- `discover_response_received -> TopicConfigPanel.on_discover_response`
- `topic_request_requested -> MqttClient.send_topic_request`
- `config_sync_requested -> MqttClient.send_config_sync`
- `config_query_requested -> MqttClient.send_config_query`

机器人状态和 discover 响应刷新时，也会同步更新：

- `CommandPanel`
- `TopicConfigPanel`
- `DataSenderPanel`

### 3.4 协议解析修复

Agent 回复 topic 请求使用：

```text
station/topic/response/{robot_id}
```

此前 `parse_station_topic()` 没有解析出 `robot_id`，导致前端收到响应时 robot_id 为空，表格无法更新。

修复后：

```python
parse_station_topic("station/topic/response/robot_001")
# {"type": "topic_response", "robot_id": "robot_001"}
```

新增测试覆盖协议解析和 MQTT dispatch。

### 3.5 Agent 配置同步语义

在 `agent/base_agent.py` 中补齐：

- 单条 `subscribe topic_request` 会更新运行时订阅、限频器、`config.subscriptions`，并写回配置。
- 单条 `unsubscribe topic_request` 会删除运行时订阅、限频器、`config.subscriptions`，并写回配置。
- `config_sync` 以地面站下发配置为准进行收敛：
  - 新配置有、当前没有：新增订阅。
  - 新配置没有、当前有：取消订阅。
  - 参数变化：重建订阅。
- `config_query` 返回当前 `subscriptions` 和 `fleet_rules`。

为了避免下发话题配置误伤编队配置，后续又调整为：`config_sync` 没有显式携带 `fleet_rules` 时，不清空或改写机器人端已有 `fleet_rules`。

## 四、地面站与机器人端配置持久化

### 4.1 地面站 transmit_config.yaml 保存

“保存配置”按钮接入：

```text
qt_frontend/config/transmit_config.yaml
```

保存时按 robot_id 分组：

```yaml
subscriptions:
  turtlebot_001:
    - topic: /scan
      msg_type: sensor_msgs/LaserScan
      freq_limit: 5.0
      transport: mqtt_binary
      compression: {}
```

设计上采用机器人端相同的 list 条目格式，只是地面站多一层 robot_id。

实现要点：

- `build_transmit_config()`：构建地面站配置。
- `normalize_transmit_subscriptions()`：兼容旧 map 格式和新 list 格式。
- `entries_from_transmit_config()`：按机器人加载本地保存配置。
- `save_transmit_config_file()`：写回 YAML。

保存后的字段顺序固定为：

1. `topic`
2. `msg_type`
3. `freq_limit`
4. `transport`
5. `compression`

使用 `yaml.safe_dump(..., sort_keys=False)` 保持字段顺序。

### 4.2 下发配置时自动保存

当前“下发配置到机器人”会自动保存地面站配置。执行顺序为：

```python
self.config_sync_requested.emit(...)
self.save_transmit_config_file(...)
self.mark_entries_saved(...)
```

也就是说点击“下发配置到机器人”会同时：

- 向机器人发送 `config_sync`。
- 将当前表格内容写入 `qt_frontend/config/transmit_config.yaml`。
- 将表格状态刷新为 `saved`。

“保存配置”则只写本地 YAML，不主动下发机器人。

### 4.3 避免本地空配置覆盖远端拉取结果

测试发现：当 `transmit_config.yaml` 为空时，点击“从机器人拉取话题”后，表格会短暂显示远端配置，然后又变为空。

根因是 `MainWindow` 收到机器人心跳后会刷新机器人列表，而旧版 `on_robot_list_changed()` 每次刷新都会重新加载本地 YAML。本地为空时，就覆盖了刚从机器人端拉取到的配置。

修复策略：

- 如果刷新前后仍是同一个机器人，不重新加载本地 YAML。
- 只有当前选中机器人发生变化时，才加载该机器人的本地保存配置。

新增测试：

```python
test_robot_list_refresh_only_reloads_when_selected_robot_changes
```

### 4.4 Agent 只替换 subscriptions 段

用户测试发现：Agent 写回 `config.yaml` 时，不仅改了 `subscriptions`，还会重排其他 YAML 内容，包括注释、空行、顺序和引号。

最终修复为文本级替换顶层 `subscriptions` 段：

- `_save_config()` 不再用 `yaml.safe_dump()` 重写整份配置。
- 先读取原 YAML 文本。
- 只替换顶层 `subscriptions:` 段。
- `robot_id`、broker 配置、注释、空行、引号风格、`fleet_rules` 等其他内容尽量保持原样。

新增测试：

- `test_save_config_only_updates_subscriptions`
- `test_save_config_preserves_yaml_text_outside_subscriptions`
- `test_config_sync_without_fleet_rules_keeps_existing_fleet_rules`

### 4.5 Docker 可写挂载

容器内 Agent 原本写 `/app/agent/config.yaml`，但 `docker-compose.yml` 将 `./agent` 只读挂载：

```yaml
- ./agent:/app/agent:ro
```

这会导致运行时订阅已经生效，但文件写不回宿主机。

为满足当前测试场景，将挂载改为：

```yaml
- ./agent:/app/agent:rw
```

注意：修改 compose volume 配置后，需要重新创建容器，单纯 restart 不会应用挂载变化。

建议命令：

```bash
docker compose up -d --force-recreate robot-turtlebot-001
```

## 六、话题状态显示调整

状态含义整理为：

- `active`：从机器人端拉取到，说明机器人当前配置中存在。
- `pending`：本地新增，还未确认保存或下发。
- `saved`：已经保存到地面站本地 YAML，或点击下发后已同步保存本地。
- `failed`：机器人返回失败，保存动作不覆盖该状态。
- `inactive`：取消订阅响应成功后的状态。

点击“保存配置”或“下发配置”后，非 `failed` 的条目会统一标记为 `saved`。

后续如果需要更直观，可以把 UI 显示改成中文：

- `active` → `已生效`
- `saved` → `已保存`
- `pending` → `待保存`
- `failed` → `失败`
- `inactive` → `已停用`
