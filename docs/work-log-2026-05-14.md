# 工作日志 — 2026年5月14日

## 整体情况

本日修复了此前遗留的 `/map` OccupancyGrid 无数据问题。问题现象是：MQTT 侧可以收到地图数据，Bridge 侧 `/turtlebot_001/map` publisher 也能注册成功，但 ROS 侧 `rostopic echo /turtlebot_001/map` 长时间收不到实际消息。

最终根因定位为 `dict_to_ros_msg.py` 中对 ROS 数组类型的处理错误：`nav_msgs/OccupancyGrid.data` 是 `int8[]`，原实现把 `int8[]` 误转成了 `bytes`，导致 ROS 序列化失败。修复后，`/turtlebot_001/map` 已能在宿主机 roscore 中正常收到并被 RViz 使用。

> Git：1 个提交，4 个文件变更（1 个新建工作日志）。

## 一、问题背景

5月9日工作日志中记录过 `/map` 的未完成项：

- MQTT 侧可通过 `mosquitto_sub` 收到 `robot/turtlebot_001/sensor/map`。
- payload 约 574KB，地图尺寸为 `384 x 384`。
- Bridge 侧 `/turtlebot_001/map` topic 存在，类型为 `nav_msgs/OccupancyGrid`。
- `rostopic info /turtlebot_001/map` 能看到 `/mqtt_ros_bridge` publisher。
- 但 `rostopic echo /turtlebot_001/map` 没有实际消息。
- 其他话题 `/odom`、`/scan`、`/imu`、`/tf`、`/joint_states` 均正常。

当时的推断方向是：Bridge 的 MQTT 回调线程、publisher 时序、大消息处理或 logging 静默异常。今天按这个顺序重新排查。

## 三、临时诊断增强

为了排查 Bridge 内部处理路径，先给 `bridge/mqtt_ros_bridge.py` 增加了两类低风险诊断能力。

### 3.1 大 payload 耗时日志

在 `_handle_sensor_data()` 中统计：

- MQTT payload 大小
- JSON decode 耗时
- `dict_to_ros_msg()` 转换耗时
- ROS publish 耗时
- publisher 当前连接数

只对大于 256KB 的 payload 记录，并且最终降为 `logger.debug()`，避免正常运行时刷屏。

### 3.2 publisher 首次连接等待

新增：

```python
def _wait_for_publisher_connection(
    self, topic: str, pub: rospy.Publisher, timeout: float = 0.5
) -> None:
    ...
```

目的：typed publisher 首次创建后，给 ROS subscriber 一个短暂连接窗口，降低大消息首帧丢失的概率。

这个增强不是最终根因修复，但对低频大消息更稳健，因此保留。

## 五、根因定位：`int8[]` 被误转为 `bytes`

继续用真实 MQTT map payload 做序列化验证：

```python
data = json.loads(payload.decode("utf-8"))
msg_type = data.pop("_msg_type")
msg = dict_to_ros_msg(data, msg_type)
buf = io.BytesIO()
msg.serialize(buf)
```

修复前输出：

```text
msg_type nav_msgs/OccupancyGrid
data len 147456
sample [-1, -1, -1, -1, -1, -1, -1, -1]
ros data type <class 'bytes'>
len 147456
sample [255, 255, 255, 255, 255, 255, 255, 255]
serialize failed SerializationError field data must be a list or tuple type. Only uint8[] can be a string
```

关键点：

- `OccupancyGrid.data` 的 ROS 类型是 `int8[]`。
- 地图未知区域使用 `-1` 表示。
- 原实现把 `int8[]` 和 `uint8[]` 一起转成 `bytes`。
- `bytes()` 无法表达 `-1`，之前通过 `b & 0xFF` 变成了 `255`。
- ROS `genpy` 只允许 `uint8[]` 使用 bytes/string 快捷表示。
- `int8[]` 必须保持 `list` 或 `tuple`。

因此 Bridge 中 `pub.publish(ros_msg)` 实际在 ROS 序列化阶段失败，导致 publisher 存在但没有消息发出。

## 六、修复内容

### 6.1 `bridge/dict_to_ros_msg.py`

修复数组转换逻辑：

```python
# uint8[] / char[] / byte[] may be represented as bytes in genpy.
# int8[] must remain a list/tuple because signed values such as
# OccupancyGrid.data can contain -1.
if base_type in ("uint8", "char", "byte") and fixed_length is None:
    return bytes(b & 0xFF for b in val)
```

修复后：

- `uint8[]` 仍可转换为 `bytes`，适合图像、二进制数据等场景。
- `int8[]` 走普通数组逻辑，保持为 `list[int]`。
- `OccupancyGrid.data` 中的 `-1` 不再丢失符号。

### 6.2 `bridge/mqtt_ros_bridge.py`

保留两项增强：

- `_wait_for_publisher_connection()`：首次发布前短暂等待 subscriber 连接。
- 大 payload debug 日志：记录 decode、convert、publish 的耗时和连接数。

这些增强不改变协议和消息内容，主要用于提高低频大消息发布稳定性和后续诊断能力。

### 6.3 `tests/test_dict_to_ros_msg.py`

新增 `TestConvertValue`，覆盖关键类型差异：

```python
def test_uint8_array_to_bytes(self):
    result = _convert_value([0, 1, 255, 128], "uint8[]")
    assert isinstance(result, bytes)
    assert result == bytes([0, 1, 255, 128])

def test_int8_array_stays_list(self):
    result = _convert_value([-1, 0, 100], "int8[]")
    assert result == [-1, 0, 100]
```

这个测试用于防止后续再次把 `int8[]` 误改为 `bytes`。
