## 三、增加不依赖 Qt 和 ROS 的 frame 策略函数

任务 1 新增了 `qt_frontend/rviz_frame_policy.py`。这个模块只处理字符串和配置字典，不导入 PyQt5、ROS、ctypes 或 MQTT 客户端，方便用普通 pytest 单测覆盖。

本模块解决了几个基础问题：

- `normalize_frame_id()` 统一去掉首尾空白和开头 `/`，避免 `husky_001/base_link` 和 `/husky_001/base_link` 两种写法混用。
- `global_fixed_frame_for()` 优先读取 `rviz.global_frame`，再兼容旧字段 `rviz.fixed_frame`，都没有时默认 `global_map`。
- `robot_fixed_frame_for()` 默认使用 `{robot_id}/base_link`，并支持 `rviz.robot_fixed_frames.<robot_id>` 为单台机器人覆盖。
- `follow_selected_robot_default()` 读取“跟随选中机器人”默认开关，未配置时默认开启。

这里的 `global_map` 是地面站侧多机器人统一显示的全局 frame。Bridge 指地面站侧 MQTT 到 ROS 的转换进程，它会把机器人端通过 MQTT 传来的数据重新发布成本地 ROS topic，并通过 fleet frame 配置把每台机器人的局部地图挂到 `global_map` 下。Agent 指机器人侧采集 ROS topic 并发送 MQTT 消息的进程，本次任务没有改 Agent。

实现时按 TDD 执行：先写 `tests/test_rviz_frame_policy.py`，确认缺少模块导致测试失败；再实现最小策略函数；最后验证 8 个测试全部通过。

## 四、在机器人列表面板增加视角控件

任务 2 扩展了 `qt_frontend/panels/robot_list_panel.py`。机器人列表面板原来只负责发现机器人、展示在线状态和选中机器人详情；今天在同一块面板中加入了 RViz 视角相关入口，因为用户切换视角的动作和“选择哪台机器人”天然相关。

新增的界面和信号包括：

- “全局视角”按钮，点击后发出 `global_frame_requested` 信号。
- “跟随选中”复选框，状态变化后发出 `follow_frame_changed(bool)` 信号。
- 当前视角标签，默认显示 `当前视角: --`，后续由 MainWindow 同步为 `global_map` 或某台机器人的局部 frame。

同时新增了三个面板公共接口：

- `follow_selected_robot_enabled()`：读取“跟随选中”是否开启。
- `set_follow_selected_robot_enabled(enabled)`：由 MainWindow 根据配置设置默认状态。
- `set_current_fixed_frame(frame)`：更新用户可见的当前 RViz 视角。

这一部分仍然不直接调用 RViz 或 ROS。面板只表达用户意图和显示状态，真正的 RViz fixed frame 切换交给 MainWindow 统一处理，这样后续如果主窗口接入方式变化，面板本身不需要理解 native RViz 细节。

## 五、主窗口接入 RViz fixed frame 切换

任务 3 把前两步串起来，修改了 `qt_frontend/main_window.py`。MainWindow 现在负责把机器人列表的用户意图转换为 RViz C++ 接口调用。

主要行为如下：

- 选中机器人时，如果“跟随选中”开启，就按策略函数推导 frame，例如 `husky_001/base_link`，并调用 RViz `set_fixed_frame()`。
- 点击“全局视角”时，把 RViz fixed frame 切回 `global_map`。
- 关闭“跟随选中”后，选中机器人仍会更新命令面板目标，但不改变 RViz 视角。
- RViz 尚未初始化时，先记录 `_pending_fixed_frame`，并更新面板上的当前视角标签。等 `_init_rviz()` 完成后再补一次实际 `set_fixed_frame()`。
- 如果 native 库暂时没有 `can_resolve_frame` 符号，Python 侧不会阻止启动，也不会阻止切换，只是跳过可解析性检查。

这里的 pending frame 是“用户已经要求切换到的 frame，但 RViz C++ widget 尚未创建完成”。记录它可以避免启动早期点击机器人或触发全局视角时丢失用户意图。

今天也在 MainWindow 测试中补了真实信号接线验证。测试不仅直接调用 `_switch_to_global_frame()` 和 `_on_robot_selected_for_rviz()`，还通过 `RobotListPanel` 的 `global_frame_requested`、`robot_selected`、`follow_frame_changed` 信号验证主窗口确实把控件接到了切换逻辑上。

任务 3 完成时，Python 侧已经预留了 `can_resolve_frame()` 的兼容调用，并在旧 native 库缺少该符号时跳过检查。后续任务 4 补齐 C++ 导出函数后，“TF 暂不可解析”的状态提示就可以基于 RViz 自己的 `FrameManager` 查询结果触发。

## 六、补充 C++ RViz frame 可解析性检查

任务 4 修改了 `qt_frontend/native/rviz_widget.h` 和 `qt_frontend/native/rviz_widget.cpp`，给嵌入式 RViz 胶水库增加 `can_resolve_frame(void* widget_ptr, const char* frame)` 导出函数。

这里的 frame 可解析性检查不是阻止用户切换视角的硬性校验，而是一个状态探测：C++ 层通过 RViz `VisualizationManager` 取到 `FrameManager`，再调用 `getTransform(frame, ros::Time(0), position, orientation)` 查询目标 frame 当前是否能转换到 RViz fixed frame。查询失败时，Python 层仍然会调用 `set_fixed_frame()` 完成切换，只是在状态栏提示“TF 暂不可解析”，等待后续 TF 到达后 RViz 自己恢复显示。

这样处理的原因是，多机器人链路中的 TF 可能晚于用户操作到达。尤其是 Agent、Bridge、静态 TF、动态 TF 分别通过不同进程或 topic 进入地面站时，前端不应该因为某一刻 TF 树不完整就拒绝用户切换视角。

实现时还补充了 native 层所需的头文件：

- `rviz/frame_manager.h`
- `OGRE/OgreVector3.h`
- `OGRE/OgreQuaternion.h`

Python 侧在任务 3 已经注册了 ctypes 签名，并用 `try/except AttributeError` 兼容旧版 `librviz_widget.so`。因此任务 4 的重点是让新构建出来的 native 库真正导出该符号，并通过源码静态测试和 C++ 编译确认接口可用。

## 八、手动测试后修复重复点击已选机器人不切换视角

在用户启动 Husky 容器和地面站前端做手动测试时，发现一个实际交互问题：第一次点击 `husky_001` 可以把 RViz fixed frame 切到 `husky_001/base_link`；点击“全局视角”后可以切回 `global_map`；但此时 `husky_001` 在机器人列表中仍处于选中状态，再点击同一行不会切回机器人视角。只有先取消并重新勾选“跟随选中”，或者先点其他机器人再点回 `husky_001`，才会再次触发切换。

这个问题的根因在机器人列表面板，而不是 MainWindow 或 RViz native 层。`RobotListPanel` 原本只监听 `QTreeWidget.itemSelectionChanged`，它只在选择项发生变化时触发。点击已经选中的同一行时，Qt 认为选择状态没有变化，因此不会发出选择变化信号，MainWindow 也就收不到新的 `robot_selected` 事件。

修复时给机器人树增加了 `itemPressed` 处理：如果用户按下的是已经选中的机器人行，就把它视为“重新选择这台机器人”，主动更新详情并再次发出 `robot_selected(robot_id)`。未选中的行仍然走原来的 `itemSelectionChanged` 路径，避免第一次点击时重复发信号。

这次修复保持了面板职责边界：机器人列表只表达“用户重新选择了某台机器人”的意图，不直接调用 RViz；MainWindow 继续根据“跟随选中”开关和 frame 策略决定是否切换 fixed frame。
