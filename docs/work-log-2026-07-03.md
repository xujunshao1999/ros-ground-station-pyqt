## 二、复核 Husky 重型仿真默认启动链路

今天首先复核 7 月 2 日新增的 Husky 仿真容器。Husky 容器的目标不是替代 Turtlebot 轻量仿真，而是提供一个更接近重型数据测试场景的机器人镜像：容器内默认启动 roscore、Gazebo、Husky 车体、Velodyne 点云、Realsense 相机、hdl_graph_slam 以及本项目的 ROS1 Agent。

这里的 Agent 指机器人端桥接进程，它订阅容器内部 ROS master 上的话题，再按配置将数据通过 MQTT JSON、MQTT 二进制或 HTTP snapshot 发送给地面站。Bridge 指地面站侧的 `bridge/mqtt_ros_bridge.py`，它从 MQTT 接收 Agent 发送的数据，再重新发布成本地 ROS topic，供 Qt 前端和 RViz 使用。这样机器人 ROS 网络和地面站 ROS master 仍然保持隔离，跨机器数据统一通过本项目协议传输。

今天确认了 Husky 服务使用独立的 `robot-husky-001` compose service，容器名为 `husky-001`。容器对外暴露 `18080:8080`，用于 HTTP snapshot 拉取重型 payload。`docker/supervisord-husky.conf` 中负责拉起 roscore、Husky SLAM 仿真和 Agent，Husky Agent 使用 `agent/configs/husky_001.yaml` 作为默认话题配置。

今天没有重新设计这套容器，而是在它的基础上完成计划进度标记、运行态验证和后续链路调优。后续前端测试、Velodyne 频率排查和 Realsense 压缩图像链路完善，都是基于这套 Husky 默认启动环境继续做的。

## 三、验证 Velodyne 点云频率并记录待确认问题

在测试 Velodyne 点云时，用户手动将 `/velodyne_points` 的频率配置调整为不主动限频，希望比较容器内原始频率和地面站侧重发布频率是否一致。

验证结果显示两侧并不一致：

- 容器内原始 `/velodyne_points` 约为 `10 Hz`。
- 地面站本地 `/husky_001/velodyne_points` 约为 `3.9 Hz`。
- MQTT meta 话题 `robot/husky_001/sensor/velodyne_points/meta` 也约为 `3.9 Hz`。

这里的 meta 是轻量提示消息，用于告诉地面站某个重型话题的最新 payload 在哪里、大小是多少、消息类型是什么。实际点云 payload 不直接放进 MQTT JSON，而是由 Agent 缓存在 HTTP snapshot 服务里，Bridge 收到 meta 后再通过 HTTP 拉取 serialized payload 并发布成本地 ROS topic。

从验证结果看，Gazebo 原始点云发布频率正常，Bridge 侧重发布频率和 MQTT meta 频率基本一致，问题更可能出现在 Agent 处理重型点云、更新 HTTP snapshot、发布 MQTT meta 的链路上。由于单帧点云约 `512 KB`，当前约 `4 Hz` 的地面站侧频率更像是 Python Agent + HTTP snapshot 链路的实际吞吐表现，而不是配置没有生效。

今天没有直接修改这个问题，而是按用户要求建立了独立问题文档：

```text
docs/issues/husky-velodyne-frequency-gap-2026-07-03.md
```

文档记录了背景、当前现象、验证命令、观察结果、初步判断和后续可排查方向。这样后续如果要优化 Velodyne 吞吐，可以从 Agent 内部统计、点云降采样、payload 压缩、长连接或分块传输等方向继续评估。

## 四、修复前端流量面板只显示部分话题的问题

运行 Husky 和地面站前端后，前端流量面板最初只显示 `slam_odom` 和 `joint_states`，没有显示 Velodyne、Realsense 点云等重型话题。排查后确认，问题不是 Husky 没有发布这些话题，而是前端流量统计主要依赖普通 sensor payload，而 `http_stream` 话题走的是另一条链路：MQTT 上只发送 meta，真实 payload 通过 HTTP 拉取。

今天将前端 MQTT 客户端和主窗口的信号分发补齐，使 sensor meta 也能进入流量面板。处理思路是：

- `qt_frontend/mqtt_client.py` 增加 `sensor_meta_received` 信号，区分普通传感器数据和重型话题 meta。
- `qt_frontend/main_window.py` 将 sensor meta 路由到流量面板，而不是当成普通传感器摘要数据展示。
- `qt_frontend/panels/traffic_monitor.py` 兼容 meta 中的 `_payload_bytes`、`payload_size`、`size_bytes` 等字段，并优先使用 meta 自带的 `transport` 标记。

这样流量面板可以统计 `http_stream` 话题的提示消息和 payload 尺寸，不再只看到轻量 MQTT JSON 话题。这个修复对 Husky 重型仿真很重要，因为 Velodyne 和 Realsense 点云默认都不适合直接通过普通 JSON 传输。

该部分已通过聚焦测试，但截至日志写入还未提交。

## 五、将 Realsense 图像改为默认压缩图像链路

在讨论 Realsense 图像传输时，确认原始图像不适合直接跨链路传输。`sensor_msgs/Image` 是未压缩图像，带宽压力明显高于压缩图像；而 Realsense 的点云是 `sensor_msgs/PointCloud2`，默认走 `http_stream`，不是图像压缩链路。

今天检查容器内 Realsense 话题后发现，原始仿真只提供 `/realsense/color/image_raw`，没有默认提供 `/realsense/color/image_raw/compressed`。因此补充了两部分能力：

第一，在 Husky 镜像中安装 `ros-noetic-compressed-image-transport`，并在 supervisor 中新增 `realsense_color_compressed` 进程。该进程等待 `/realsense/color/image_raw` 出现后，使用 ROS 的 `image_transport republish` 生成：

```text
/realsense/color/image_raw/compressed
```

第二，在 Husky Agent 配置中默认订阅压缩图像：

```yaml
- topic: /realsense/color/image_raw/compressed
  msg_type: sensor_msgs/CompressedImage
  freq_limit: 5.0
  transport: mqtt_binary
  qos: 0
  compression: {}
```

这里选择 `mqtt_binary`，是因为压缩图像本身已经是 JPEG 这类压缩后的二进制数据，不应该再转成 JSON。进一步排查时发现，协议层原本没有把 `sensor_msgs/CompressedImage` 放进 ROS1 serialized 二进制通道白名单中。只改配置会导致 Agent 仍可能退回 JSON 路径。今天因此补充了协议层支持，让 `sensor_msgs/CompressedImage` 通过现有的 `ros1_serialized_v1` 二进制通道发送。

运行态验证后，MQTT 上能够看到压缩图像 envelope 和 `/bin` 二进制 payload。地面站本地 ROS 上也能看到：

```text
/husky_001/realsense/color/image_raw/compressed
```

并且 `format` 字段为：

```text
"rgb8; jpeg compressed bgr8"
```

这说明 Realsense RGB 图像已经走压缩图像链路，而不是原始 Image 链路。
