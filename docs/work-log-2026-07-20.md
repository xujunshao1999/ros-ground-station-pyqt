## 二、目标 Agent 支持乱序二进制消息配对

二进制编队消息分为两部分发送：`envelope` 是携带路由、消息类型、ROS MD5、字节数和有效期的轻量 JSON 说明，其中 ROS MD5 是 ROS 消息定义的指纹，用于确认源端与目标端的消息结构一致；`binary body` 是带 13 字节 `FRB1` 关联头的 ROS1 serialized 字节，关联头由 4 字节魔数、1 字节版本和 8 字节 `transfer_id` 组成。ROS1 serialized 指 ROS 消息对象按 ROS1 原生格式序列化后的字节，目标 Agent 可以直接反序列化，避免字典和 JSON 往返转换。两部分通过 64 位 `transfer_id` 关联，因此不依赖 MQTT 跨 topic 的到达顺序。

今日将 BaseAgent 的 MQTT 接收入口改为先按 topic 类型分流。`/bin` payload 直接作为 bytes 处理，不再尝试 UTF-8 解码。主 topic 的 envelope 则会校验 MQTT topic 中的源、目标与 `Message.src/dst` 是否一致，避免异常路由消息进入配对缓存。

接收缓存同时加入了资源和时间边界：

- envelope 和 body 允许任意一侧先到，配对完成后才调用 ROS hook；
- 单侧缓存有效期为 2 秒，各限制 256 条；
- 单个 body 最大 8 MiB，body 缓存总量最大 64 MiB；
- TTL 是消息的网络有效期，编队 ROS topic 默认为 1 秒，envelope 入缓存和完成配对后各检查一次；
- 缓存锁只保护清理、插入、弹出和计数，ROS 反序列化与发布在锁外执行。

这些处理解决了 binary body 先到、envelope 先到、任一侧丢失、异常大 payload 和旧消息占用内存等问题。Mock Agent 也提供了无 ROS 的 binary hook，便于在没有 roscore 的环境检查 MQTT 分流边界。

## 三、源 Agent 按规则选择 JSON 或 ROS1 Serialized

原有实现为每条编队规则创建一个 ROS subscriber。多个目标转发同一个源 topic 时，会重复订阅、序列化和转字典。今日改为按 `(src_topic, msg_type)` 合并 route，同一源 topic 只保留一个 subscriber，但每个目标仍独立执行频率限制、transport、QoS 和 frame 策略。

一次 ROS 回调中：

- 存在到期 binary route 时，ROS message 只执行一次 `serialize()`；
- 多个 binary route 共用 serialized bytes，但每个 route 生成独立 `transfer_id`；
- 存在 JSON route 或 binary 无法使用时，ROS message 只转换一次字典；
- ROS serialize 失败或源端无法获取 MD5 时，该 binary route 自动回退到完整 MQTT JSON；
- MQTT `publish().rc` 失败不触发 JSON 回退，避免 QoS 1 队列在重连后再次投递而造成重复。

这里的自动回退不是让新建规则默认使用 binary。旧规则和 Qt 新建规则仍默认 `mqtt_json + QoS 1`，只有用户明确选择 `mqtt_binary` 时才使用二进制数据面。

## 四、目标 Agent 反序列化并发布到本地 ROS

目标 ROS1Agent 在配对完成后先加载 `msg_type` 对应的 ROS message class，并校验本地 `_md5sum` 与 envelope 中的源端 MD5 完全一致。MD5 缺失、不一致、未知消息类型或 `deserialize()` 失败时，只丢弃当前 transfer，不影响后续消息。

反序列化成功后，Agent 按 `dst_topic + msg_type` 复用 ROS publisher。`frame_policy=namespace` 时，会将 header、child frame 和 TF transforms 中的 frame 加上源机器人前缀，并保持幂等，避免多机器人 frame 冲突。`/fleet/incoming` 只发布来源、目标 topic、消息类型、transport、transfer ID 和 payload 大小等轻量摘要，不复制完整 ROS payload。

## 五、Qt 面板和示例配置形成闭环

编队通信面板增加了“传输方式”和“QoS”控件，规则表扩展为 11 列，可直接看到每条规则的 transport 和 QoS。新建规则默认 JSON/QoS1；高频连续状态可显式选择 binary/QoS0；从 YAML 加载、表单编辑、保存、下发到配置响应回填都保留 QoS 0，不再因默认值判断被误改为 1。

三份 Agent YAML 和地面站 `transmit_config.yaml` 的 fleet 示例同步到当前协议：

- `/odom` 高频状态示例使用 `mqtt_binary + QoS 0`；
- `/move_base_simple/goal` 低频关键目标使用 `mqtt_binary + QoS 1`；
- 所有示例仍保持 `enabled: false`，容器启动时不会自动产生跨机器人流量。

## 六、真实双 Turtlebot 验收与限频修正

今日使用两个真实 ROS Noetic Turtlebot3 仿真容器完成端到端验收。系统中已有两个 6 天前退出的原容器，为了不删除或覆盖它们，验收使用 `/tmp/fleet-compose.override.yaml` 将新容器命名为 `fleet-test-turtlebot-001/002`。容器通过 Compose 相对挂载直接使用功能 worktree 的 `protocol/` 和 `agent/`，不是 `master` 旧代码。

源机器人 `/odom` 在仿真时钟下约为 30 Hz。通过与 Qt 面板相同的 `station/turtlebot_001/config/sync` 协议下发了唯一启用规则：`/odom` -> `turtlebot_002` -> `/fleet/turtlebot_001/odom`，10 Hz，`mqtt_binary`，QoS0，namespace。配置查询响应确认 fleet 规则已生效，原 subscriptions 没有被配置同步覆盖。

首次测量时，MQTT envelope 约为 8.27 Hz，目标 ROS topic 65 秒平均约为 8.25 Hz，未达到计划的 9 Hz 门槛。边界对比表明频率在源 Agent 转发前就已降低，不是 MQTT、目标配对或 ROS 发布继续丢帧。

根因是旧限频器每次发送后都把基准设为“迟到的实际回调时刻”。当 Gazebo 在墙钟下只能给出约 24 Hz 回调时，10 Hz 规则被量化为每 3 帧发送一次，实际只有 8 Hz 左右。修正后按理论周期推进基准；回调抖动不再累积相位偏差，长时间停顿时会跳过已错过周期，每次回调仍最多只发当前帧，不会产生追赶式突发。

修正后用相同配置复测：

- 20 条 envelope 从首条到第 20 条约 1.888 秒，折算约 10.06 Hz；
- 目标 `/fleet/turtlebot_001/odom` 的 65 秒平均约为 10.01 Hz；
- envelope 均为 `binary=true`、`transport=mqtt_binary`、`encoding=ros1_serialized_v1`；
- 实际 Odometry MD5 为 `cd5e73d190d741a2f92e81eda573aca7`，payload 为 718 字节，20 条 transfer ID 均不同；
- 每条 binary MQTT payload 为 718 字节 ROS body 加 13 字节关联头，20 条实际 MQTT payload 合计 14,620 字节；
- `mosquitto_sub` 为每条输出追加了 1 字节换行，因此抓包输出文件为 14,640 字节，其中检测到 20 个 `FRB1` 头；
- 目标 ROS header 的 `frame_id` 为 `turtlebot_001/odom`，namespace 策略生效。

验收结束后，已用测试前备份恢复 `turtlebot_001.yaml` 和 `turtlebot_002.yaml`，重启确认后删除独立测试容器和临时 Compose 网络。功能 worktree 没有残留临时 `enabled: true` 或 10 Hz 运行态配置，用户原有的两个退出容器也保持原状态。
