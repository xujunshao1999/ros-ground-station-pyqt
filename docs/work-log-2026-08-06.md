## 二、将固定模式区改为可配置命令区

原来的模式区写死了“自动、手动、返航、急停”等操作，只能发送固定 mode 指令。模式区内的急停还与顶部“全部急停”重复，无法利用已经完成的四槽位配置和自定义 ROS 消息参数。

命令面板现在从 `command_buttons.yaml` 加载四个固定位置。未配置的位置显示“未配置”并保持禁用；已配置位置显示用户保存的文字、ROS topic 和消息类型。过长文字会显示省略号，tooltip 中仍保留完整文字、topic 和消息类型。设置齿轮固定在在线机器人数量旁边，四个按钮采用稳定的 2×2 布局。原有九宫格速度控制继续只面向当前选中的单台机器人，顶部“全部急停”也保留原来的专用路径。

点击已配置按钮后，面板会生成唯一 `exec_id`。它是一次命令执行的编号，用于把发出的命令与机器人返回的确认对应起来。面板不直接访问 MQTT，而是发出批量命令请求，由主窗口决定实际发送目标。

新增的批次跟踪器按机器人记录等待、成功、失败和超时状态。机器人返回的 `cmd_ack` 是命令确认消息，其中包含 `exec_id`、执行结果和错误说明。5 秒后仍未确认的机器人会被标记为超时；旧批次的迟到确认不会覆盖当前界面，已完成历史也设置了数量上限，避免长期运行后状态无限增长。存在失败或超时时，结果区可以查看逐台详情。

配置文件损坏时，面板会回退到四个空位置并显示读取错误，不会因为启动时解析异常导致整个主窗口无法构造。

## 三、统一在线状态并完成多机器人发送

接入正式主窗口前，机器人状态和 discover 响应会分别刷新多个面板，话题配置面板也单独接收 discover，存在重复更新同一份在线列表和话题目录的风险。这里的 discover 是地面站向机器人获取可用 ROS topic 和消息类型的发现过程。

机器人列表面板现在只在在线集合真正变化时发出 `online_robots_changed`。重复心跳只更新时间和状态，不重复刷新所有下游面板；机器人首次上线、discover 发现新机器人或心跳超时离线时，才把排序后的在线列表统一分发给命令面板、话题配置、编队通信、数据发送、传感器摘要和顶部在线数量。在线集合变空时，各面板也会同步清除旧机器人。

主窗口在创建面板前建立一个共享 `RobotTopicCatalog`。它是按机器人保存 discover 话题和消息类型的前端目录，同一个实例同时交给命令设置窗口和话题配置面板。discover 响应先更新目录，再更新机器人在线状态；原来 MQTT discover 直接连接话题配置面板的重复路径已经删除，编队通信面板的既有兼容连接继续保留。

消息结构查询也接入正式入口。这里的 schema 是机器人根据本地 ROS 消息定义返回的递归字段结构，前端用它生成参数表单。主窗口负责转发 discover 请求、schema 查询和 schema 响应，使设置窗口能够在线选择 topic、自动填入消息类型并校验参数。

发送批量命令时，主窗口先确认 MQTT 已连接且至少存在一台在线机器人，再按机器人 ID 排序启动批次。每台机器人收到相同 `exec_id` 的 `custom` 指令，参数格式为 `{topic, msg_type, data}`。每次发送都使用独立的参数深拷贝，某台机器人发送过程不能修改后续机器人的 payload；payload 指 MQTT 消息实际承载的数据内容。未连接或没有在线机器人时，面板直接显示拒绝原因，不创建空批次，也不调用发送接口。

`MqttClient.send_cmd()` 的往返测试确认调用方给出的 `exec_id` 会原样保留。单机器人速度控制和顶部全部急停没有改为新批次逻辑，原有行为保持不变。

## 四、复核协议与最终实现

功能接线完成后，对照任务 1 至任务 10 的最终代码复核了 `docs/protocol.md`。消息结构查询和响应分别使用：

```text
station/{robot_id}/message_schema/query
station/{robot_id}/message_schema/response
```

两者均使用 QoS 1。查询和响应字段与 `MessageSchemaQueryData`、`MessageSchemaResponseData` 一致；文档已经说明 256 KiB schema 上限，以及 robot ID、`request_id` 和 `msg_type` 三重匹配的防乱序规则。

`custom.params` 在文档和实现中统一为 `{topic, msg_type, data}`。机器人端 Agent 会按 `msg_type` 创建真实消息类型的 ROS Publisher，并递归把 `data` 转换为 ROS 消息，不会隐式包装成 `std_msgs/String`。如果确实需要发送字符串，必须明确使用 `std_msgs/String` 及对应的 `{"data": "文本"}` 参数。

本次没有发现协议字段、topic、QoS、大小边界或真实 ROS 发布语义不一致，因此没有修改权威协议文档。
