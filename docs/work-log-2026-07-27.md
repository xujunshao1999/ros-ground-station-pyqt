## 二、先解决自动表单缺少字段来源的问题

设置窗口计划采用“递归自动表单 + JSON 高级编辑”两种方式。自动表单可以让普通用户直接填写字段，JSON 模式则留给熟悉消息结构的用户处理复杂参数。实现这一交互前，首先要解决一个实际问题：地面站本身不知道机器人安装了哪些自定义消息包，也不知道每个消息类型下面有哪些字段。

这里的消息结构后续统一称为 schema，它表示一个 ROS 消息的字段树。例如 `geometry_msgs/Twist` 下有 `linear` 和 `angular`，这两个字段下面又分别有 `x`、`y`、`z`。地面站拿到这棵树后，才能逐层生成输入控件。

今天先在共享协议中增加了查询和响应消息。地面站向某一台机器人发送 `message_schema_query`，机器人处理后返回 `message_schema_response`。每次查询都带有 `request_id` 和 `msg_type`，响应会原样带回这两个值，避免用户快速切换类型时，较早返回的结果覆盖当前表单。

查询和响应采用单独的 MQTT topic，并使用 QoS 1。QoS 1 的含义是消息至少送达一次，适合这种低频但不能轻易丢失的控制请求。响应中同时规定了成功和失败格式：成功时返回完整字段树，失败时返回明确错误，不能只静默丢弃。为避免异常消息定义占用过多带宽，schema 的 JSON 编码大小限制为 256 KiB。

这部分完成后，地面站与机器人之间已经有了一套明确、可测试的“查询消息字段”协议，后续界面不需要自己约定临时 JSON 格式。

## 三、让机器人从本地 ROS 环境生成字段结构

协议定义完成后，下一步是让机器人真正回答查询。机器人端的 Agent 是连接本机 ROS 与 MQTT 的桥接程序，它能够访问本机已经安装并 source 的 ROS 消息包，因此字段结构应由 Agent 在机器人本地生成，而不是由地面站猜测。

今天新增了递归解析逻辑。它会读取 ROS 消息类中的字段名和字段类型，把基础数值、字符串、时间、时长、数组以及嵌套消息整理成统一结构。对于嵌套消息，会继续向下展开；对于定长数组，也会保留长度信息。这样后续前端不只可以生成一层表单，也能处理消息中套消息、消息数组等情况。

实现过程中重点处理了异常消息定义带来的资源风险。如果消息类型循环引用自身，或者嵌套层级、字段数量异常，单纯递归可能造成无限展开或内存占用。现在解析深度最多为 12 层，总字段数最多为 512 个，递归过程中再次遇到当前类型会立即报错。消息类中的字段名和字段类型数量不一致时，也不会生成一份看似成功但实际残缺的结构。

为了在没有 roscore 的环境中跑单元测试，测试里使用了 fake ROS 消息类，只模拟 ROS 消息类提供的字段信息。MockAgent 是不依赖 ROS 的模拟机器人程序，它为 `geometry_msgs/Twist` 和 `std_msgs/Bool` 提供稳定示例，便于前端链路继续开发。这里的 fake 和 Mock 只用于验证字段解析与协议处理，不代表真实自定义消息包已经联调通过。

这部分完成后，ROS1Agent 已经可以读取机器人本地真实消息类型，MockAgent 也能支持无 ROS 开发流程，为后续自动表单提供了稳定的数据来源。

## 四、把自定义指令从字符串包装改为真实 ROS 消息

继续检查现有指令执行逻辑时发现，原来的 `action: custom` 虽然名字叫“自定义”，实际却固定发布 `std_msgs/String`，并把参数字典转成一段 JSON 文本。这样只能把内容当字符串发出去，无法真正发布 `my_pkg/Control`、`geometry_msgs/Twist` 等用户选择的消息类型。

今天将 custom 指令格式固定为 `topic`、`msg_type` 和 `data` 三部分。ROS1Agent 收到指令后，会根据 `msg_type` 加载真实 ROS 消息类，把 `data` 递归转换成消息对象，再发布到指定 topic。如果确实需要发送 `std_msgs/String`，也要明确选择该类型并填写它的 `data` 字段，不再进行隐式 JSON 字符串包装。

转换过程中增加了严格模式，主要用于拦截手工 JSON 或配置中的错误。未知字段、数组形状不对、定长数组长度不符、嵌套消息不是 object、布尔值被当成数字，以及基础类型转换失败时，Agent 会返回带完整字段路径的错误，不会把错误数据继续交给 ROS。原有 Bridge 和机器人间数据转发仍使用兼容模式。这里的 Bridge 指地面站侧把 MQTT 传感器数据重新发布到本地 ROS master 的转换程序，因此本次严格校验不会改变既有传感器和编队链路行为。

还补充了 topic、消息类型、JSON object 和 256 KiB 大小校验。ROS1Agent 与 MockAgent 使用相同的协议边界，但 MockAgent 只确认格式正确，不会假装已经在 ROS 中完成发布。

实际使用中，同一组按钮可能频繁向少量 topic 发送消息。如果每次点击都新建 ROS Publisher，不但浪费资源，也可能产生大量无效连接。今天增加了最多 32 项的 LRU 缓存。LRU 表示优先淘汰最久没有使用的对象：相同 topic 和消息类型会复用已有 Publisher；同一 topic 改变类型时会注销旧对象；超过 32 项时会清理最久未使用的一项。转换、创建或发布失败只影响当前指令，Agent 停止时也会统一清理这些 Publisher。

完成这部分后，按钮配置中的消息类型和参数已经能够对应到真实 ROS 发布行为，而不是停留在前端标识或字符串占位上。

## 五、接通地面站向机器人的字段查询

前面已经具备查询协议和机器人端解析能力，但地面站 MQTT 客户端与 Agent 还没有真正订阅和分发这些消息。今天继续把这段链路接通。

Agent 连接 Broker 后，现在会订阅只属于本机的消息结构查询 topic。收到请求时同时检查 MQTT topic 中的机器人 ID、JSON 消息外层的目标机器人、消息类型、请求编号和 ROS 消息类型格式。只有目标确实是本机时才执行解析；发给其他机器人的请求会直接忽略，不能误调用本机 ROS 环境。

解析成功后，Agent 通过 QoS 1 返回字段结构。消息类型不存在、解析过程报错、返回内容不是 object 或 schema 超过 256 KiB 时，则返回标准错误响应。这样前端以后可以把具体原因显示在设置窗口，而不是一直停留在加载状态。

Qt MQTT 客户端增加了发送 schema 查询的方法，并在连接 Broker 后订阅所有机器人的响应。这里使用的 MQTT wildcard 是通配订阅规则，`station/+/message_schema/response` 中的 `+` 可以匹配任意一个机器人 ID。该 topic 仍由共享协议模块统一生成，没有在前端各处手工拼接。

收到响应后，客户端会再次核对 MQTT topic 类型和 JSON 消息类型，确认 data 是 object 后才发出 Qt signal。Qt signal 是 MQTT 网络线程向界面线程传递结果的通知机制，后续设置窗口可以监听它，并根据 `request_id` 判断这是不是当前正在等待的查询。

这部分完成后，地面站已经可以向指定机器人发起消息字段查询，并接收成功结构或失败原因。自动表单尚未实现，但它依赖的远程查询链路已经具备。
