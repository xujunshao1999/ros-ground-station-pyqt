## 一、Docker 化 Turtlebot3 仿真环境

### 1.1 架构设计

```
Docker 容器 (turtlebot-001)              宿主机
┌──────────────────────────────┐       ┌─────────────────┐
│  roscore                      │       │ mosquitto (MQTT) │
│  turtlebot3_gazebo (世界+模型) │       │                  │
│  gmapping (SLAM 建图)         │  MQTT │ mqtt_ros_bridge  │
│  RViz (3D 可视化)             │◄─────►│ roscore (宿主机)  │
│  agent (ROS→MQTT 桥接)        │       │ Qt 前端 + RViz   │
└──────────────────────────────┘       └─────────────────┘
```

容器内运行独立 roscore，与宿主机 roscore 完全隔离，通过 MQTT broker 通信。Gazebo 和 RViz 通过 X11 socket 转发到宿主机显示。

**`docker/supervisord-turtlebot3.conf`**（新建）— 容器内进程管理

定义 4 个 supervised 程序，按依赖顺序启动：

| 程序 | 职责 | 启动策略 |
|---|---|---|
| `roscore` | 容器内 ROS Master | `autorestart=true`，就绪判定 3s |
| `agent` | ROS → MQTT 桥接，`ROBOT_ID` / `BROKER_HOST` 从环境变量注入 | `autorestart=true`，就绪判定 5s |
| `turtlebot3` | 启动 `turtlebot3_world.launch`（含障碍物世界） | 等待 roscore 就绪 后启动，`autorestart=true` |
| `slam` | 启动 `turtlebot3_slam.launch slam_methods:=gmapping`（内置 bringup + gmapping + RViz） | 等待 roscore 就绪 后启动，`autorestart=true` |

关键设计决策：
- turtlebot3 和 slam 两个程序启动前均通过 `until rostopic list &>/dev/null; do sleep 1; done` 轮询等待 roscore 就绪，解决竞态条件
- 使用 `LIBGL_ALWAYS_SOFTWARE=1` 强制 Mesa 软件渲染，规避 Intel iris 驱动的 CCS 3D 纹理 bug
- slam 程序使用 `turtlebot3_slam.launch` 而非 `turtlebot3_gmapping.launch`，因为前者内置 `turtlebot3_remote.launch`（bringup），提供 robot_state_publisher + URDF 加载，后者仅启动 gmapping 节点

## 二、MQTT-ROS Bridge 数据流修复

### 2.1 问题分析

经过端到端数据流追踪，发现 Bridge 层存在两个结构性缺陷：

**缺陷 1：TF 话题路由错误**

```
Agent 端（容器内）:
  /tf (tf2_msgs/TFMessage) → MQTT robot/turtlebot_001/sensor/tf

Bridge 端（宿主机）:
  接收 MQTT → 还原 ROS 消息 → 发布到 /turtlebot_001/tf

RViz（宿主机）:
  订阅 /tf → 收不到任何数据 ✗
```

根因：Bridge 将所有传感器数据发布到 `/{robot_id}/{topic}`（如 `/turtlebot_001/tf`），但 RViz 的 TF Display 只订阅标准话题 `/tf` 和 `/tf_static`。这导致 RViz 完全看不到机器人的坐标变换链。

**缺陷 2：未注册传感器被降级为 raw JSON**

当 Bridge 的 `_topic_map` 中没有某话题的条目时（例如 Station 尚未显式订阅），传感器数据被当作 `std_msgs/String` 原样转发，丢失类型信息。而 Agent 端已在每个消息中注入 `_msg_type` 字段（`base_agent.py:297`），Bridge 却完全忽略了它。

### 2.2 修复方案

**`bridge/mqtt_ros_bridge.py`**（核心改动）

重构 `_handle_sensor_data` 方法，新流程：

```
解码 JSON（前置）
  → 查 _topic_map
    → 找到：使用已注册的 ros_topic + msg_type
    → 未找到：从 _msg_type 字段自动检测消息类型
      → 成功：推算 ros_topic
      → 失败：回退到 JSON String（保持向后兼容）
  → 弹掉 _msg_type（清理内部字段）
  → 特殊话题路由判断：
      tf / tf_static / joint_states → 发布到标准 ROS 话题 /tf、/tf_static、/joint_states
      其他话题 → 发布到 /{robot_id}/{topic}
  → dict_to_ros_msg 还原为类型化 ROS 消息
  → 发布
```

新增 `_prefix_tf_frames` 方法：多机器人场景下给 frame_id 添加命名空间前缀（如 `turtlebot_001/odom`），由 `namespace_tf_frames` 配置控制，默认关闭，不影响单机器人使用。

新增特殊话题集合 `_CANONICAL_TOPICS = frozenset({"tf", "tf_static", "joint_states"})`，这些话题需要路由到 ROS 标准命名空间。

### 2.3 话题注册表扩展

**`protocol/topic_registry.py`** — `_BUILTIN_REGISTRY` 从 19 种扩展到 41 种

新增覆盖 RViz 全部常用 Display 类型：

| 分类 | 新增类型 | 数量 |
|---|---|---|
| std_msgs | `Float64`、`ColorRGBA` | +2 |
| geometry_msgs | `PointStamped`、`PolygonStamped`、`PoseArray`、`PoseWithCovarianceStamped`、`AccelStamped`、`WrenchStamped` | +6 |
| sensor_msgs | `JointState`、`Range`、`MagneticField`、`FluidPressure`、`Temperature`、`Illuminance`、`RelativeHumidity`、`TimeReference`、`CameraInfo` | +9 |
| nav_msgs | `GridCells`、`OccupancyGrid` (HEAVY) | +2 |
| visualization_msgs | `Marker`、`MarkerArray` | +2 |
| 遗留支持 | `PointCloud` (HEAVY) | +1 |

所有类型均按数据量合理分层（LIGHT → MQTT JSON，HEAVY → HTTP Stream），传感器类型配有适当的默认限频（如 `JointState` 50Hz、`Range` 10Hz）。
