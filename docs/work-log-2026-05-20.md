## 二、多机器人桥接方案梳理

今日先围绕原 TCP 桥接替换方案进行了架构梳理。当前目标不是深度集成某个多机探索算法，而是让地面站成为通用 ROS topic 跨机器人转发与统一坐标显示系统。多机探索算法仍在各机器人本地运行，地面站只理解 `robot_id`、`topic`、`msg_type`、`frame_id` 和转发配置，不理解算法内部语义。

核心结论如下：

- 当前系统可以替代旧 TCP 桥接，但需要补齐 `fleet_rules`、`FleetData`、入站/出站类型化 ROS topic 转发和坐标 frame 处理闭环。
- 机器人间数据应优先走 `robot/{src}/to/{dst}`，不经过 Qt 前端中转。
- 地面站侧需要支持 `global_map -> robot_i/map` 这类 fleet 静态 TF，用于多机器人统一可视化。
- 真实旧算法暂时不可用时，可以先用两个 Turtlebot3 容器验证多机器人接入、话题隔离、frame 命名空间和 `/odom` 跨机器人转发。

随后将该设计保存为计划文档：

- `docs/superpowers/plans/2026-05-20-fleet-topic-and-frame-unification.md`

## 三、双 Turtlebot3 测试容器

为验证多机器人链路，在 `docker-compose.yml` 中新增 `robot-turtlebot-002` 服务。该服务复用现有 Turtlebot3 仿真镜像和 `docker/supervisord-turtlebot3.conf`，只调整：

- `container_name: turtlebot-002`
- `ROBOT_ID=turtlebot_002`

新增后通过以下命令验证 Compose 配置：

```bash
docker compose config --services
```

输出包含：

```text
robot-turtlebot-001
robot-turtlebot-002
```

测试过程中发现两个 Turtlebot 容器都挂载宿主机 `./agent` 到容器内 `/app/agent`。如果两个 Agent 都使用默认 `agent/config.yaml`，则给 `turtlebot_002` 下发话题配置时，会覆盖共享的机器人端配置文件。为此调整 Turtlebot3 supervisord 启动命令，为每个机器人使用独立配置路径：

```text
/app/agent/configs/turtlebot_001.yaml
/app/agent/configs/turtlebot_002.yaml
```

同时修复 `AgentConfig.from_yaml()`：当配置文件尚不存在时，也会保留传入的 `config_path`，确保首次保存时写入目标独立配置文件，而不是回退到默认 `agent/config.yaml`。

## 四、Docker 配置权限问题

多容器测试时还发现由容器创建的 `agent/configs` 目录和 YAML 文件在宿主机上可能显示为 `nobody:nogroup`，导致普通用户无法直接修改或删除。曾尝试通过 Compose 的 `user: 1000:1000` 让容器按宿主机用户运行，但这会影响 Turtlebot3/Gazebo 图形环境，导致启动后不显示界面，因此已撤回该方案。

当前采用更局部的处理方式：

- 容器仍按原来的 root 方式运行，避免破坏 Gazebo/X11 环境。
- Agent 保存配置后，如果运行用户为 root，会尝试将写出的配置文件属主调整为父目录属主。
- 已经由容器创建且属主异常的目录，需要在宿主机手动执行一次：

```bash
sudo chown -R $(id -u):$(id -g) agent/configs
```

该问题属于 Docker bind mount 的运行环境问题，不影响实际机器人部署。实际机器人通常每台机器一份代码和一份本地 `agent/config.yaml`，不需要拆分 `agent/configs/<robot_id>.yaml`。

## 五、FleetData 协议扩展

为支持通用 ROS topic 跨机器人转发，扩展了 `protocol/messages.py` 中的 `FleetData`。新增字段包括：

- `src_topic`：源机器人本地 ROS topic。
- `dst_topic`：目标机器人本地发布 topic。
- `msg_type`：ROS 消息类型。
- `frame_policy`：frame 处理策略，当前支持 `preserve` 和 `namespace`。
- `stamp`：数据时间戳。

这些字段均提供默认值，保持旧的 `position`、`nav_goal`、`custom` 和 `pointcloud` 用法兼容。

对应测试新增了 `test_fleet_data_ros_topic_fields`，验证 `MessageFactory.fleet_data()` 能正确序列化 ROS topic 转发所需字段。

## 六、坐标 frame 命名空间工具

为多机器人可视化和跨机器人 topic 转发提供统一 frame 处理，新增 `agent/frame_utils.py`：

- `namespace_frame_id(frame_id, robot_id)`
- `namespace_message_frames(data, robot_id)`

当前覆盖以下常见字段：

- `header.frame_id`
- `child_frame_id`
- `transforms[].header.frame_id`
- `transforms[].child_frame_id`

工具函数保持幂等。例如：

```text
base_scan -> turtlebot_001/base_scan
/base_scan -> turtlebot_001/base_scan
turtlebot_001/odom -> turtlebot_001/odom
```

随后修改 `bridge/mqtt_ros_bridge.py`，让 Bridge 在 `namespace_tf_frames` 开启时，不再只处理 `tf2_msgs/TFMessage`，而是对所有带 frame 字段的 ROS 消息统一执行命名空间化。这样 `/odom`、`/scan`、`/map` 等普通消息中的 `header.frame_id` 也会和 `/tf` 保持一致，避免 RViz 中 TF 树和普通显示 topic 的 frame 不匹配。

## 七、fleet_rules 出站转发

在 `agent/base_agent.py` 中新增 `fleet_rules` 规范化与应用逻辑：

- `_normalize_fleet_rules()`：清洗规则结构，过滤缺少 `src_topic`、`msg_type` 或有效 `targets` 的规则。
- `_apply_fleet_rules()`：提供子类钩子，由具体 Agent 创建 ROS 订阅。
- `config_sync` 显式携带 `fleet_rules` 时，规范化、保存并应用规则。
- `config_sync` 未携带 `fleet_rules` 时，继续保留机器人端已有编队规则，避免话题配置下发误删编队配置。
- 启动恢复订阅时，也会恢复并应用持久化的 `fleet_rules`。

在 `agent/ros1_agent.py` 中实现 ROS1 出站转发：

- 新增 `_fleet_subscribers`，与地面站普通话题订阅 `_ros_subscribers` 分离。
- 根据每条 enabled rule 订阅本机 `src_topic`。
- 使用 `ros_msg_to_dict()` 将 ROS 消息转换为 dict。
- 构造 `FleetData(data_type="ros_topic")`，填入 `src_topic`、`dst_topic`、`msg_type`、`frame_policy` 和 payload。
- 按 `targets` 调用 `send_to_robot()`，发布到 MQTT `robot/{src}/to/{dst}`。
- 根据 `freq_limit` 做出站限频，避免高频 topic 无控制转发。

该部分为后续替代旧 TCP 桥接的出站半链路。

## 八、fleet_data 入站类型化发布

继续实现 `FleetData(data_type="ros_topic")` 在目标机器人端的入站处理。此前 ROS1Agent 收到 fleet 数据后只发布 JSON 到 `/fleet/incoming`，适合调试，但不能让算法直接订阅类型化 ROS topic。

今日新增行为：

- 校验 `dst_topic`、`msg_type` 和 dict payload。
- 当 `frame_policy == "namespace"` 时，使用发送方 `src_id` 对 payload 中的 frame 字段加命名空间。
- 使用 `dict_to_ros_msg(payload, msg_type)` 还原类型化 ROS 消息。
- 发布到 `dst_topic`。
- 按 `(dst_topic, msg_type)` 缓存 publisher，避免每条消息重复创建。
- 保留 `/fleet/incoming` 调试 JSON 发布。

这样目标机器人可以直接订阅类似：

```text
/fleet/turtlebot_001/odom
```

而不是只能解析 `/fleet/incoming` 里的 JSON。
