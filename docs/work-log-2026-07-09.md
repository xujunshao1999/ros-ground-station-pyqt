## 二、明确普通话题和公共 TF 话题的边界

今天延续了前一天对 ROS topic 传输策略的验证结果。Bridge 是地面站侧把 MQTT 数据重新发布成本地 ROS topic 的组件；canonical topic 在这里指不加机器人命名空间、直接发布到标准公共名称的话题。Bridge 侧此前把 `/tf`、`/tf_static` 和 `/joint_states` 都当成 canonical topic，发布到标准公共 topic。复盘后认为这个规则对 TF 是合理的，但对 `joint_states` 不合适。

`JointState` 主要描述关节名称、位置、速度和力矩。多机器人场景下，如果多台机器人把同名关节都发布到公共 `/joint_states`，地面站侧会更难区分来源。相比之下，TF 的公共话题仍然有必要保留，因为 RViz 和 TF 工具链默认从 `/tf`、`/tf_static` 消费坐标树，实际隔离依赖 frame_id 命名空间。

因此今天确认并保留的规则是：

- `/tf` 和 `/tf_static` 继续发布到公共 ROS topic；
- `/joint_states`、`/hdl_graph_slam/odom`、`/velodyne_points` 等普通传感器或状态话题发布到 `/{robot_id}/{original_topic}`；
- 例如 Husky 的 `/joint_states` 在地面站本地应落到 `/husky_001/joint_states`。

这一点也被写入话题健康面板计划中，作为后续 UI 里“本地 ROS”列的推导依据。

## 三、重新设计“摘要面板”为“话题健康面板”

今天对现有摘要面板做了一次重新定位。原来的摘要面板会把最新消息内容做简单摘要，例如 LaserScan、OccupancyGrid、JointState 的字段概览。但在当前链路里，用户更需要知道话题是否健康，而不是在右侧窄面板里读一段消息摘要。

新的设计把面板职责收敛为：

- `Hz` 不再作为总览主列，只放到详情里作为辅助诊断；
- 下方详情展示 transport、encoding、payload format、payload size、stream URL、本地 ROS topic 和诊断说明；
- 摘要内容仍保留为“补充摘要”，但不再是面板主价值。

## 四、把面板主视图改成面向排障的健康总览

实现时先处理了本地 ROS topic 的统一推导和健康快照字段。`SensorSummaryPanel.local_ros_topic_for()` 现在集中表达一条规则：`/tf`、`/tf_static` 保持公共 topic，其余话题加机器人命名空间。这个函数后续被总览表、等待态详情和快照构建复用，避免各处各写一套 `/husky_001/joint_states` 这类路径拼接逻辑。

随后扩展了 `TopicSnapshot`。此前快照更像“最新消息摘要”，主要记录消息类型、摘要、时间和帧数；健康面板需要回答的问题更多，例如实际使用 `mqtt_json`、`mqtt_binary` 还是 `http_stream`，payload 是什么编码，Bridge 最后应该发布到哪个本地 ROS topic，当前状态是正常、等待数据、断流还是配置不一致。因此今天把 `transport`、`expected_transport`、`encoding`、`payload_format`、`payload_size`、`stream_url`、`local_ros_topic`、`health_status` 和 `diagnostic` 纳入快照。

这一步的取舍是：第一版不读 ROS master，也不在前端调用 `rostopic`。健康面板只基于前端已经收到的 MQTT envelope、HTTP stream meta 和订阅配置做判断。这样能先把链路诊断闭环做起来，同时避免 UI 引入 ROS 环境依赖或额外阻塞。

总览表也从“内容摘要表”改成了更适合窄面板的健康视图。原来表格列数偏多，右侧区域宽度不够时会挤在一起；今天把它收敛成 `话题`、`机器人`、`健康`、`更新`、`本地 ROS` 5 列。顶部指标区也不再突出 `Hz`，改成 `健康`、`本地 ROS`、`更新` 和 `消息数`。`Hz` 仍然保留，但放到详情里作为辅助诊断信息，而不是和流量面板争主视角。

这里还修了计划自检时发现的一个关键问题：等待数据时还没有运行时 MQTT envelope，不能用展平后的 `sensor_name` 去反推本地 ROS topic。比如配置里的原始 topic 是 `/hdl_graph_slam/odom`，Agent 侧 MQTT sensor name 可能已经变成 `hdl_graph_slam_odom`。如果用后者推导，会丢掉原始层级。今天在 `ObservedTopic` 中保留订阅配置的原始 `ros_topic`，所以等待态也能正确显示 `/husky_001/hdl_graph_slam/odom`，不会等到第一帧数据到达后才显示正确目标。

## 五、把详情区从消息摘要改成健康诊断

总览表收窄后，下方详情区承担更多诊断信息。今天新增 `_detail_browser` 作为健康详情展示区域，同时保留 `_browser` 兼容旧测试和旧调用习惯。这样界面行为已经切到新详情区，但改动范围没有扩散到主窗口之外。

详情内容从“消息内容摘要优先”改成“健康字段优先”。选中话题后，用户可以看到机器人 ID、话题名、消息类型、健康状态、更新间隔、`transport`、`encoding`、`payload_format`、`payload_size` 和本地 ROS 发布目标。原来的 LaserScan、OccupancyGrid、JointState 等消息摘要没有直接删除，而是降级为“补充摘要”。这样既保留了快速辨认消息内容的能力，也不会让摘要信息遮住真正用于排障的字段。

这个调整主要面向实际使用场景：地面站操作时，使用者通常先想知道“这个话题有没有来”“为什么 RViz 看不到”“Bridge 会发到哪里”，而不是先读一段 ROS message 字段概览。详情区现在能直接对应这些问题，例如 `/joint_states` 的目标会显示为 `/husky_001/joint_states`，`mqtt_binary` envelope 会显示编码和 payload 大小，断流时会提示多久没有收到新消息。

## 六、把 HTTP stream 大数据链路纳入健康视图

今天还把 HTTP stream meta 接入了健康面板。`sensor_meta` 是 Agent 针对大 payload 话题发出的取数说明，不是完整 ROS message 本体。点云这类数据如果直接塞进 MQTT JSON 会很重，所以 Agent 会缓存 payload，并通过 meta 告诉地面站 `transport=http_stream`、`stream_url`、编码格式和 payload 大小；Bridge 再根据这个 URL 拉取真实数据。

此前这类 meta 主要进入流量面板，健康面板看不到它，导致用户只能知道有流量统计，却不容易判断 HTTP snapshot 链路本身是否正常。今天改成 `MainWindow._on_sensor_meta()` 同时把 meta 分发给健康面板和流量面板：流量面板继续负责带宽、累计流量和吞吐趋势；健康面板负责显示 stream URL、实际 transport、本地 ROS topic 和诊断状态。

这个拆分让两个面板的职责更清楚。比如 `/velodyne_points` 走 `http_stream` 时，健康面板会告诉用户 meta 已经到达、Bridge 目标是 `/husky_001/velodyne_points`、payload 有多大、取数 URL 是什么；流量面板则继续回答它占了多少带宽、是否是当前主要流量来源。

## 七、补上订阅配置和实际传输不一致的诊断

最后处理的是配置不一致问题。订阅配置里可以明确写 `transport`，例如 `mqtt_json`、`mqtt_binary` 或 `http_stream`，也可以写 `auto`。如果配置明确要求 `mqtt_json`，但实际收到的是 `mqtt_binary` envelope，健康面板应该把它标出来，否则用户只看到“有数据”，却不知道这条链路已经偏离配置预期。

今天在 `ObservedTopic` 中记录配置里的期望 transport，并在构建 `TopicSnapshot` 时写入 `expected_transport`。当期望值不是空、不是 `auto`，并且与实际 transport 不一致时，健康状态会显示为 `配置不一致`，诊断信息会写明“期望 mqtt_json，实际 mqtt_binary”。这样问题可以直接落到配置层，而不是让用户去猜是 Agent、Bridge 还是前端展示出了偏差。

同时特意保留了 `transport: auto` 的例外规则。`auto` 在本项目里表示让系统按消息类型和运行时 envelope 自动选择传输方式，所以它不应该因为实际落到 `mqtt_binary` 或 `http_stream` 就被标成错误。今天为这条规则单独补了测试，避免后续把 `auto` 误当成普通明确配置。
