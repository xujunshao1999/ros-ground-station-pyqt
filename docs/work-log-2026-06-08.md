## 二、TF 链路一致性检查

今日在仅启动 `turtlebot_001` 的情况下，对容器内 ROS 网络与地面站本地 ROS 网络中的 TF 链路进行了对比。排查目标是确认 RViz 看到的 TF 是否来自 Bridge 重新发布后的地面站本地 topic，而不是直接依赖机器人容器内 ROS master。

检查内容包括：

- 查看地面站本地 `/tf` 和 `/tf_static` 的发布订阅关系。
- 使用 `tf_echo` 验证 `global_map -> turtlebot_001/map`、`turtlebot_001/map -> turtlebot_001/base_scan` 等关键链路。
- 对比容器内 `/scan`、`/tf` 频率与地面站本地 `/turtlebot_001/scan`、`/tf` 频率。
- 清理历史残留的诊断节点，避免旧的 `tf_echo` 订阅者干扰判断。

结论是：地面站前端看到的是 Bridge 侧重新发布到本地 roscore 的 TF，核心坐标链路可用；但高频 TF 经 Agent 序列化、MQTT 转发和 Bridge 反序列化后，频率明显低于容器内原始 `/tf`。

## 三、重复静态 Transform 与多机器人影响

今日也分析了重复静态 transform 记录在多机器人场景下的影响。静态 TF 本身是 latched/retained 语义，重复发布同一条静态 transform 通常不会改变数学结果，但在多机器人系统中有两个风险：

- 如果不同机器人没有正确命名空间化 frame，例如都发布 `base_link -> base_scan`，会在地面站本地 TF 树中产生 frame 冲突。
- 如果 Bridge 侧缓存和重发静态 TF 时只按 `child_frame_id` 覆盖，而没有区分机器人来源，可能导致某台机器人的静态 link 被另一台机器人覆盖。

当前链路的安全边界是：机器人 frame 需要在 Bridge 侧统一加上 `robot_id/` 前缀，并且 `/tf_static` 通过 retained MQTT 和 Bridge 缓存重发，晚加入的 RViz 或 `tf_echo` 订阅者也能拿到完整静态 TF 集合。运行态排查中也确认了重复记录本身不是今日卡顿的主要来源。

## 四、前端速度控制优化

此前命令面板发送速度需要先拖动速度条，再点击发送，临场控制不够直接。今日将速度控制改为八向按钮交互：

- 中心按钮用于停止。
- 上、下、左、右和四个斜向按钮分别发送对应线速度和角速度组合。
- 支持低、中、高三档速度步进。
- 按下方向按钮立即发送速度命令，释放时发送停止命令。
- 未选中机器人时方向按钮保持禁用，避免误发命令。

对应测试覆盖了速度档位映射、方向到速度的转换、选中机器人后的命令发出，以及未选中机器人时按钮禁用等行为。该部分已提交为 `e95f734 feat: 优化前端速度控制`。

## 五、TF 与 LaserScan 卡顿排查

用户反馈地面站前端显示 TF 和 LaserScan 不顺畅。今日从 ROS topic 频率、MQTT 转发采样和运行进程三个方向排查。

排查中观察到的关键现象：

- 容器内 `/scan` 基本稳定在 5Hz。
- 地面站本地 `/turtlebot_001/scan` 一度低于容器内频率。
- 容器内 `/tf` 频率约为 80Hz 量级，地面站本地 `/tf` 约为 20Hz 量级。
- 机器人容器内同时运行 Gazebo GUI 和 RViz 会占用额外资源，对仿真和转发稳定性不利。

运行态上做了两类调整：

- 将 `/tf` 和 `/scan` 的 `freq_limit` 调整为 `0.0`，并将高频传感器数据的 MQTT QoS 调整为 `0`，降低排队和确认开销。
- 将 TurtleBot3 仿真容器调整为 headless 运行，关闭 Gazebo GUI 和容器内 RViz，减少与地面站 RViz 重复渲染造成的资源竞争。

调整后，`/scan` 在地面站侧恢复到接近 5Hz 的稳定状态；`/tf` 仍明显低于容器内原始频率，说明剩余瓶颈主要在 Agent 通用 `ros_msg_to_dict()`、JSON 编码、MQTT 传输和 Bridge 还原链路，而不是前端单独造成。

上述 TF/Scan 优化目前保留为运行态配置，尚未作为代码提交固化。

## 六、选中机器人详情区域修复

今日修复了地面站前端“选中机器人详情”区域的三个问题：

- 位姿和速度只在切换选中机器人时刷新，后续同一机器人 `status` 更新不会刷新详情。
- 电量区域同时存在“电量:”文本行和电量进度条，视觉上重复。
- 电量条虽然有 UI，但此前用户难以确认它是否绑定真实状态数据。

修复后，`RobotListPanel` 在收到已选中机器人的状态更新时，会同步刷新详情区域的位姿、速度和电量；详情刷新逻辑被抽为 `_update_detail()`，取消选择时通过 `_clear_detail()` 恢复占位状态。电量展示删除了重复的 `QLabel("电量:")`，只保留进度条自身的 `电量 %v%` 格式，并将 `status.battery` 通过 `_battery_percent()` 限制在 `0-100` 范围内。

需要注意的是，电量条现在已经绑定到机器人状态数据；如果机器人端 `battery` 字段本身来自模拟值或固定值，前端会如实显示该值，不会自行生成真实电量。

该部分已提交为 `eebf021 fix: 修复机器人详情刷新`。
