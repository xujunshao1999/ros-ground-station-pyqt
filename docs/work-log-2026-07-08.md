# 工作日志 — 2026年7月8日

## 一、今日概览

今日主要围绕 ROS 话题跨机器传输策略进行了重构和验证。此前项目里不少常规 ROS topic 仍默认走 `mqtt_json`，也就是机器人端 Agent 先把 ROS 消息转换成 JSON，再通过 MQTT 发给地面站 Bridge。这种方式可读性好，但对 `Odometry`、`JointState`、TF、图像等结构化消息不够合适，容易造成 JSON 膨胀，也会让 Bridge 重建 ROS 消息时丢失原始序列化结构。

今天将默认策略调整为：控制、配置、状态和简单标量继续走 `mqtt_json`；常规 ROS topic 默认走 `mqtt_binary`，payload 使用 ROS1 原生序列化格式 `ros1_serialized_v1`；点云、OctoMap、PCL 等大数据继续走 `http_stream`，MQTT 只发送 meta 信息，真实 payload 通过 HTTP snapshot 拉取。

## 二、协议注册表默认策略改为普通 ROS 话题走二进制

第一项工作是调整 `protocol/topic_registry.py`。这个文件负责根据 ROS 消息类型决定默认传输方式。此前 `LIGHT` 基本等同于“轻量消息走 JSON”，导致 `nav_msgs/Odometry`、`sensor_msgs/Imu`、`sensor_msgs/JointState`、`geometry_msgs/PoseStamped` 等常规 ROS topic 仍会默认解析为 `mqtt_json`。

今天改为用更明确的策略表达默认行为：

- `std_msgs/String`、`std_msgs/Bool`、`std_msgs/Float64` 等简单标量和文本消息保留 `mqtt_json`。
- `geometry_msgs/*`、`nav_msgs/*`、`sensor_msgs/*`、`tf/*`、`tf2_msgs/*` 等常见 ROS 包使用包级通配符规则默认走 `mqtt_binary`。
- `sensor_msgs/PointCloud2`、`sensor_msgs/PointCloud`、`pcl_msgs/*`、`octomap_msgs/*` 等大 payload 明确走 `http_stream`。
- 未注册但形如 `custom_msgs/Thing` 的合法 ROS 消息类型默认走 `mqtt_binary`。

这里的“包级通配符规则”不是 shell 文件匹配，而是注册表内部根据消息类型字符串做匹配。例如 `sensor_msgs/*` 会匹配 `sensor_msgs/Image` 和 `sensor_msgs/JointState`，但精确规则仍优先，所以 `sensor_msgs/PointCloud2` 会先命中 `http_stream`。

配套测试新增并更新了 `tests/test_protocol_registry.py`，覆盖普通 ROS topic、简单 `std_msgs`、大 payload 和未知消息类型的默认传输方式。

## 三、Agent 支持普通 ROS 话题的 serialized fast path

第二项工作是扩展 `protocol/binary_payloads.py` 和 ROS1 Agent 的相关测试。此前 `is_ros_message_binary_supported()` 主要依赖少量白名单，只允许 `/tf`、`/odom`、`/imu`、`sensor_msgs/CompressedImage` 等类型走 ROS1 serialized 路径。这样即使注册表把普通 ROS topic 解析成 `mqtt_binary`，Agent 也可能因为白名单不足而退回 JSON 转换。

今天将判断逻辑改为：只要消息类型字符串是合法 ROS 消息类型，就默认允许 `ros1_serialized_v1`。实际能否工作由运行时验证：Agent 需要能拿到 ROS 消息对象并调用 `serialize()`，Bridge 需要能导入相同消息类并 `deserialize()`。

同时保留了 `LaserScan` 和 `OccupancyGrid` 的既有专用 binary 编码兼容逻辑。也就是说，专用编码能力还在，但普通 ROS topic 默认可以直接使用 ROS1 原生序列化。

测试中重点确认了三件事：

- 未知 ROS 消息类型默认允许走 serialized。
- `/joint_states` 配置为 `mqtt_binary` 后，回调优先调用 `_serialize_ros_message()` 并发布 `publish_sensor_binary_data()`，不会进入 JSON 转换。
- 如果 ROS1 原始序列化失败，Agent 会继续降级到 `ros_msg_to_dict()` 和 JSON 发布路径，避免单条异常消息中断话题发布。

第三项工作是完善 `qt_frontend/panels/topic_config_panel.py`。前端话题配置面板原来允许用户选择 `AUTO`，但用户看不到 `AUTO` 最终会解析成 `mqtt_json`、`mqtt_binary` 还是 `http_stream`。在默认策略变更后，这会增加配置理解成本，尤其是点云和普通 ROS topic 的区别不够直观。

前端测试覆盖了 Husky 发现话题场景：选择 `/odom` 时预览 `mqtt_binary`，选择 `/velodyne_points` 时预览 `http_stream`。

## 七、MQTT 与 ROS 验证结果

普通 ROS topic 走 MQTT binary 的验证命令：

```bash
timeout 12 mosquitto_sub -h localhost -t robot/husky_001/sensor/hdl_graph_slam_odom -C 1
timeout 12 mosquitto_sub -h localhost -t robot/husky_001/sensor/joint_states -C 1
```

结果均拿到 binary envelope。`/hdl_graph_slam/odom` 的 MQTT 消息包含：

```json
{"binary": true, "topic": "/hdl_graph_slam/odom", "msg_type": "nav_msgs/Odometry", "encoding": "ros1_serialized_v1", "payload_format": "ros1_serialized"}
```

`/joint_states` 的 MQTT 消息包含：

```json
{"binary": true, "topic": "/joint_states", "msg_type": "sensor_msgs/JointState", "encoding": "ros1_serialized_v1", "payload_format": "ros1_serialized"}
```

点云继续走 HTTP stream 的验证命令：

```bash

```

结果拿到 `sensor_meta`，其中 `transport` 为 `http_stream`，`encoding` 为 `ros1_serialized_v1`，`payload_format` 为 `ros1_serialized`，`stream_url` 为 `http://localhost:18080/stream/velodyne_points`。

本地 ROS topic 验证命令：

```bash
rostopic list
timeout 8 rostopic echo -n 1 /husky_001/hdl_graph_slam/odom/header
timeout 8 rostopic echo -n 1 /husky_001/velodyne_points/header
timeout 8 rostopic echo -n 1 /joint_states/header
```

结果：

- `rostopic list` 中出现 `/husky_001/hdl_graph_slam/odom`、`/husky_001/velodyne_points`、`/joint_states`、`/tf`、`/tf_static`。
- `/husky_001/hdl_graph_slam/odom/header` 能读到消息，`frame_id` 为 `husky_001/hdl_odom`。
- `/husky_001/velodyne_points/header` 能读到消息，`frame_id` 为 `husky_001/velodyne`。
- `/joint_states/header` 能读到消息。

计划中原本写的是验证 `/husky_001/joint_states/header`。实际运行时该 topic 不存在，`timeout 8 rostopic echo -n 1 /husky_001/joint_states/header` 返回超时并提示该 topic 尚未发布。排查 Bridge 代码后确认这是现有设计：`bridge/mqtt_ros_bridge.py` 将 `tf`、`tf_static` 和 `joint_states` 放在 canonical topic 集合中，发布到标准 `/tf`、`/tf_static` 和 `/joint_states`，而不是 `/{robot_id}/joint_states`。因此这里不是传输策略失败，而是计划中的本地 ROS topic 预期与 Bridge 当前命名规则不一致。

## 八、将关节状态话题改为按机器人隔离

运行态验证后继续复盘 `/joint_states` 的命名规则。`JointState` 消息主要包含关节名、关节位置、速度和力矩等信息。它不像 TF 那样必须通过公共 `/tf` 和 `/tf_static` 让 RViz 的 TF Display 自动合成坐标树；多机器人场景下，如果多台同型号机器人都把同名关节发布到公共 `/joint_states`，反而容易混在一起。

基于这个判断，今天又把 Bridge 的 canonical topic 集合从 `{"tf", "tf_static", "joint_states"}` 调整为只保留 `{"tf", "tf_static"}`。这样地面站本地 ROS 中：

- `/tf`、`/tf_static` 继续使用标准公共话题，隔离依赖 frame 命名空间，例如 `husky_001/base_link`。
- `/joint_states` 改为普通 ROS topic，Bridge 会发布到 `/{robot_id}/joint_states`，例如 `/husky_001/joint_states`。
- JSON 路径和 ROS1 serialized binary 路径都使用同一套命名规则，避免不同传输方式落到不同本地 ROS topic。

配套补充了 `tests/test_mqtt_ros_bridge.py` 中的两个回归测试：一个覆盖 JSON `sensor_msgs/JointState`，一个覆盖 `ros1_serialized_v1` 的 `sensor_msgs/JointState`。两个测试都先在旧行为下失败，实际旧发布目标是 `/joint_states`；修改 Bridge 后通过，确认发布目标变为 `/robot_001/joint_states`。

这项修正已提交为 `11ec7ad fix: 隔离joint_states发布话题`。需要注意的是，修正后尚未重新启动 Husky 容器和地面站链路做完整运行态复测；当前证据来自 Bridge 单元测试和相关回归测试。后续再次运行 Husky 验证时，应检查：

